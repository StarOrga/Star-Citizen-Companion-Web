# D02 · Löschen scheitert in der Datenbank — Umsetzungsplan (Option A: Eine Korrektur-Migration)

> Für eine lokale Claude-Code-Session im Repo star-citizen-companion-web. Einfügen mit: „Setz .claude/audit/2026-09-26-full-app/plans/D02.md um.“

## Entscheidung

- **Gewählt: Option A · „Eine Korrektur-Migration“** (Aufwand M), wörtlich:
  „Trigger erlauben das einmalige Nullsetzen (5). Fremdschlüssel mit ON DELETE SET NULL (108). Aufräumjob zählt nur fertige Builds (113). Eindeutige Pin-Plätze (111). Log-Tabellen werden beschnitten (319, 344). Fehlende Indizes auf Fremdschlüsseln (321).“
- **Empfehlung war A**, keine Abweichung. Keine Owner-Notiz.
- Hinweis aus dem Konzept: „AUD-102 (database.types neu generieren) braucht die Supabase-CLI mit Projektzugang, also deinen Rechner.“ AUD-102 gehört nicht zu Option A; es steht unter „Bewusst nicht Teil“ und als optionaler Owner-Schritt.
- Allgemeiner Owner-Wunsch: ein teilbarer Plan für eine lokale Session statt der Umsetzung. Dieser Plan bündelt alle DB-Änderungen in **einer** Migrationsdatei, wie gewählt. Dazu kommen drei kleine Begleitänderungen außerhalb von SQL, ohne die die Findings nicht vollständig geschlossen wären:
  - Größenlimit für `detail` in `ingest-telemetry` (zweite Hälfte von AUD-344)
  - Retry bei 23505 in `hangar.service.ts` (AUD-111)
  - Filter „nur fertige Builds“ in `codex.service.ts` (AUD-113)

## Ziel und Definition of Done

- **Löschen funktioniert wieder:**
  - Eine je geteilte oder übernommene Hangar-Konfiguration lässt sich löschen (`deleteConfig`).
  - Ihr Schiff lässt sich entfernen (`removeShip`, Cascade).
  - Ein Konto, das geteilt hat oder einer Freigabe folgt, lässt sich löschen (`delete-user`).
  - Folge-Kopien werden dabei zu eigenständigen Kopien (`follows_owner = false`, `forked_at` gesetzt). Share-Links verlieren nur ihre Quelle.
- **Alle übrigen Schutzregeln** der Trigger `hangar_ship_configs_share_guard` und `hangar_share_links_revoke_guard` gelten unverändert; die Negativtests unten beweisen das.
- Ein Collaborator mit Supersede-Uploads lässt sich löschen: `p4k_bundles.disabled_by` wird dann `null`.
- **Build-Retention:**
  - `prune_codex_builds` zählt nur finalisierte Builds (neue Spalte `codex_builds.finalized_at`, gesetzt von `set_current_codex_build`).
  - Ein laufender oder abgebrochener Import verdrängt nie den vorherigen LIVE-Build.
  - Nie finalisierte, nicht aktuelle Builds verschwinden nach 7 Tagen.
  - Holotable-Patch-Auswahl und Inline-Diff zeigen nur finalisierte Builds.
- **Pins und Aktivierung:** Konkurrierende Pins oder Aktivierungen aus zwei Geräten enden nicht im rohen 23505-Text. Der Service lädt neu und versucht es genau einmal erneut. Die DB-Eindeutigkeit der Pins existiert schon (siehe Vorab prüfen).
- **Log-Tabellen:**
  - `api_request_log` wird täglich auf 1 Tag beschnitten.
  - `telemetry_events` wird täglich auf 120 Tage beschnitten. Die 90-Tage-Ansicht im Admin-Dashboard (`WINDOWS = [7, 30, 90]` in `src/app/admin/telemetry-stats.component.ts:87`) bleibt vollständig, 30 Tage Puffer.
  - `detail` eines Ereignisses ist höchstens 4 KiB groß.
- **Indizes** auf `hangar_share_links.source_config_id`, `hangar_ship_configs.source_config_id`, `hangar_ship_configs.owner_user_id` (und `p4k_bundles.disabled_by`).
- Die Migration läuft auf einer frischen lokalen DB durch, lässt sich wiederholen, und die Szenarien unten verhalten sich wie beschrieben.
- Gates grün: `npm run typecheck`, `npm test`, `npm run test:gate`, `npm run build`, `node --test supabase/functions/ingest-telemetry/_detail.test.ts`.

### Schritt 2 — Abschnitt A: Trigger erlauben das einmalige Nullsetzen (AUD-005)

Datei: die Migration aus Schritt 1.

Änderung: Beide Funktionen per `create or replace function` neu anlegen. **Den vollständigen Body aus `20260920160000_hangar_loadout_sharing.sql` übernehmen** und nur die markierten Stellen ändern. Die Trigger selbst zeigen schon auf diese Funktionen und bleiben stehen.

1. `public.hangar_ship_configs_share_guard()`, UPDATE-Zweig `if not v_internal` (Original Zeilen 178–183). Die beiden Immutable-Prüfungen werden ersetzt durch:
   ```sql
   if new.source_config_id is distinct from old.source_config_id then
     -- AUD-005: the one permitted change. The owner deleted the source config
     -- and the FK action `on delete set null` detaches this copy. A copy that
     -- lost its source cannot follow it any more: it forks, irreversibly.
     if old.source_config_id is not null and new.source_config_id is null then
       if old.follows_owner then
         new.follows_owner := false;
         new.forked_at := coalesce(old.forked_at, now());
       end if;
     else
       raise exception 'source_config_id is immutable' using errcode = '42501';
     end if;
   end if;
   -- AUD-005: owner_user_id references auth.users ON DELETE SET NULL too —
   -- deleting the sharer's account must not fail on the follower's row.
   if new.owner_user_id is distinct from old.owner_user_id
      and not (old.owner_user_id is not null and new.owner_user_id is null) then
     raise exception 'owner_user_id is immutable' using errcode = '42501';
   end if;
   ```
   `shared_channel`, `shared_patch_version`, die Sperre gegen `follows_owner` false→true, die Auto-Fork-Regel und der INSERT-Zweig bleiben **wörtlich** gleich.
2. `public.hangar_share_links_revoke_guard()`: am Anfang des Bodies (vor der ersten Prüfung, Original Zeile ~302) einfügen:
   ```sql
   -- AUD-005: FK action `on delete set null` when the owner deletes the source
   -- config. Allowed only if literally nothing else on the row changes.
   if old.source_config_id is not null and new.source_config_id is null
      and (to_jsonb(new) - 'source_config_id') = (to_jsonb(old) - 'source_config_id') then
     return new;
   end if;
   ```
   Ohne diesen frühen Ausstieg würde auch die Prüfung `new.revoked_at is null → 'revoked_at may only be set, never cleared'` jede Nullsetzung auf einem nicht widerrufenen Link abweisen.
3. Die `comment on function`-Texte um „AUD-005: one-way null via FK action allowed“ ergänzen.

Hintergrund: PostgreSQL führt referenzielle Aktionen als normale UPDATEs aus, die Row-Trigger auslösen. `hangar.internal_write` setzen nur die RPCs, also greift der Guard auch bei der FK-Aktion. Die Trigger feuern alphabetisch; `hangar_ship_configs_share_guard` läuft vor `hangar_ship_configs_updated_at`.

Prüfen nach D01-B1 (lokal, als `postgres` vorbereiten):
- Nutzer A und B anlegen. A bekommt `hangar_ships`, Konfiguration `C1` und einen `hangar_share_links`-Eintrag mit `source_config_id = C1`.
- Für B im selben Block `set local hangar.internal_write = 'on';`, dann eine Folge-Konfiguration mit `source_config_id = C1`, `owner_user_id = A`, `follows_owner = true` einfügen.
- `delete from hangar_ship_configs where id = C1;` läuft durch. Bei B ist dann `source_config_id is null`, `follows_owner = false`, `forked_at is not null`. Beim Link ist `source_config_id is null`, alles andere unverändert.
- Szenario neu aufbauen. `delete from hangar_ships where id = <As Schiff>;` (Cascade) läuft durch.
- Szenario neu aufbauen. `delete from auth.users where id = A;` läuft durch, bei B ist `owner_user_id is null`.
- Negativtests als B (`set local role authenticated`, Claims mit `sub = B`), jeweils Fehler 42501:
  - `update hangar_ship_configs set source_config_id = '<andere id>' where …`
  - `… set owner_user_id = '<A>'` (auf einer Zeile mit null)
  - `… set follows_owner = true` (nach dem Fork)
  - `… set shared_channel = 'x'`
- Als A: `update hangar_share_links set loadout = '[]' …` → 42501. `… set revoked_at = now()` → ok (einmal).
- Die Datei zweimal ausführen.

### Schritt 3 — Abschnitt B: Fremdschlüssel `disabled_by` mit ON DELETE SET NULL (AUD-108)

Datei: die Migration.

Änderung:
```sql
-- AUD-108: the only FK to auth.users without an ON DELETE action. Every
-- supersede writes disabled_by = uploader, so deleting that collaborator
-- failed with a FK violation. Look the constraint up by definition (it is
-- auto-named), drop it, re-add it with ON DELETE SET NULL. Re-runnable: the
-- lookup also finds the constraint this block created.
do $$
declare v_con text;
begin
  for v_con in
    select c.conname
    from pg_constraint c
    join pg_attribute a on a.attrelid = c.conrelid and a.attnum = any (c.conkey)
    where c.conrelid = 'public.p4k_bundles'::regclass
      and c.contype = 'f'
      and a.attname = 'disabled_by'
  loop
    execute format('alter table public.p4k_bundles drop constraint %I', v_con);
  end loop;
end $$;

alter table public.p4k_bundles
  add constraint p4k_bundles_disabled_by_fkey
  foreign key (disabled_by) references auth.users (id) on delete set null;
```
Die Spalte ist schon nullable. ROLLBACK: dieselbe Constraint ohne `on delete`.

Prüfen nach D01-B1: Nutzer X anlegen. Eine `p4k_bundles`-Zeile mit `uploaded_by = <anderer Nutzer>` und `disabled_by = X` einfügen, `delete from auth.users where id = X;` läuft durch, danach ist `disabled_by is null`. `select pg_get_constraintdef(oid) from pg_constraint where conname = 'p4k_bundles_disabled_by_fkey';` zeigt `ON DELETE SET NULL`. Die Datei zweimal ausführen.

### Schritt 4 — Abschnitt C: Aufräumjob zählt nur fertige Builds (AUD-113)

Datei: die Migration.

Änderung:
1. **Spalte und einmaliger Backfill**, nur beim ersten Lauf, damit ein erneuter Lauf nie einen gerade laufenden Import als „fertig“ markiert:
   ```sql
   do $$
   begin
     if not exists (
       select 1 from information_schema.columns
       where table_schema = 'public' and table_name = 'codex_builds' and column_name = 'finalized_at'
     ) then
       alter table public.codex_builds add column finalized_at timestamptz;

     end if;
   end $$;
   comment on column public.codex_builds.finalized_at is
     'Set by set_current_codex_build (ingest-catalog finalize). NULL = import still running or abandoned — never counted by prune_codex_builds, swept after 7 days.';
   ```
2. `public.set_current_codex_build(uuid)`: Body aus `00008_codex_catalog.sql:324-338` übernehmen. Das zweite UPDATE wird zu:
   ```sql
   update public.codex_builds
     set is_current = true, finalized_at = coalesce(finalized_at, now())
     where id = p_build_id;
   ```
   Danach wieder `revoke all on function public.set_current_codex_build(uuid) from public, anon, authenticated;`.
   Das ist der einzige Aufrufer: `supabase/functions/ingest-catalog/index.ts` Op `finalize` (`admin.rpc('set_current_codex_build', …)`). Die Edge Function bleibt unverändert.
3. `public.prune_codex_builds(int)`, gleiche Signatur, `create or replace`:
   ```sql
   return query
   with ranked as (
     select b.id, b.is_current,
            row_number() over (partition by b.channel order by b.created_at desc) as rn
     from public.codex_builds b
     where b.finalized_at is not null or b.is_current
   ),
   doomed as (
     select r.id from ranked r where r.rn > p_keep and not r.is_current
     union
     select b.id from public.codex_builds b
     where b.finalized_at is null and not b.is_current
       and b.created_at < now() - interval '7 days'
   )
   delete from public.codex_builds d
   using doomed x
   where d.id = x.id
   returning d.id, d.channel, d.patch_version;
   ```
   Spalten immer qualifizieren: `channel` und `patch_version` sind zugleich OUT-Parameter von `returns table`. Danach wieder `revoke all … from public, anon, authenticated;`.
   Der Cron-Job `codex-build-retention` (`30 3 * * *`) bleibt unverändert und ruft weiter `prune_codex_builds(2)` auf.
4. Den Kopfkommentar von `20260925010000` **nicht** ändern, angewandte Migrationen bleiben historisch. Stattdessen im neuen Kopf erklären, warum `entity_counts` als Marker nicht taugt.
