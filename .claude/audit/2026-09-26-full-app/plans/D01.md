## Ziel und Definition of Done

- Der Bucket `feedback-images` ist privat (`storage.buckets.public = false`), die bucketweite Lese-Policy `feedback_images_public_read` ist weg. Lesen dürfen nur: der eigene Upload-Ordner, Admins, und die Autorin/der Autor eines Nutzer-Themas für Anhänge in Nachrichten des eigenen Themas (`feedback_author_messages`).
- Admin-Board, Autor-Panel, Composer (auch wiederhergestellte Entwürfe), Lightbox und Datei-Links zeigen Anhänge über **signierte URLs** (Laufzeit 1 h). Alte Nachrichten mit öffentlichen URLs im Body funktionieren ohne Datenmigration.
- Nach dem `db:push` liefert eine öffentliche Anhang-URL (`…/storage/v1/object/public/feedback-images/…`) keinen Inhalt mehr.
- Die Feedback-Routine kann Screenshots weiterhin lesen: `node scripts/routine-gate.mjs attachment --url <url>` legt die Datei lokal ab.
- `ingest-telemetry` antwortet `503 {"error":"server_misconfigured"}`, wenn `TELEMETRY_HMAC_KEY` oder `TELEMETRY_HASH_SALT` fehlt, außer lokal mit `TELEMETRY_DEV=1`. Im Produktionspfad steht kein Dev-Literal mehr.
- Uploader-Tag-Builds (`data-uploader-v*`) backen `SC_TELEMETRY_HMAC_KEY` ein. Der Build bricht laut ab, wenn das Secret fehlt. Ein leerer Wert wird nie zum HMAC-Schlüssel `""`. Eine abgelehnte Telemetrie steht als `warn` in `main.log`.
- Eine Session kann eine eigene `profiles`-Zeile nur mit Viewer-Neutralwerten anlegen.
- `public.is_admin(uuid)` ist für `anon` und `authenticated` nicht mehr ausführbar. Die API-Token-Verwaltung für Admins funktioniert weiter.
- `/uploader/auth` übergibt Token erst nach einem Klick auf „Verbinden“. „Abbrechen“ übergibt nichts. Vor dem Klick wird kein Desktop-Refresh-Token erzeugt.
- Gates grün: `npm run typecheck`, `npm test`, `npm run test:gate`, `npm run build`, die neuen `node --test`-Dateien, `npm --prefix data-uploader run typecheck` und `npm --prefix data-uploader test`.

#### B2 · Reine Hilfsmodule für Edge Functions, getestet mit `node --test`

- Deno-spezifisches (`Deno.env`, `Deno.serve`) bleibt in `index.ts`. Testbare Logik kommt in ein Geschwistermodul mit Unterstrich, z. B. `supabase/functions/ingest-telemetry/_config.ts`. Muster: `supabase/functions/ingest-skins/_r2-usage.ts`.
- Der Test heißt `<modul>.test.ts` daneben und importiert nur `node:test` und `node:assert/strict`. - Env-Zugriff wird als Funktion übergeben (`get: (name) => string | undefined`), damit der Test ohne Deno läuft.

#### B3 · Konventionen für neue Migrationen

- Datei per `npm run db:migration:new -- <name_in_snake_case>` anlegen. Das ist `supabase migration new` und legt `supabase/migrations/<UTC-JJJJMMTTHHMMSS>_<name>.sql` an; dafür braucht es keinen Projektzugang.
- Kopf wie in `20260920160000_hangar_loadout_sharing.sql` und `20260925010000_codex_build_retention.sql`: Dateiname, WHY, WHAT, `IDEMPOTENT: safe to re-run`, `ROLLBACK: …`. Dazu die Alpha-Datenpolitik: Wird etwas gelöscht, steht es im Kommentar; `auth.users` und `profiles` behalten immer ihre Daten.
- Idempotent schreiben: `create … if not exists`, `create or replace function`, `drop policy if exists` vor jedem `create policy`, `drop trigger if exists` vor `create trigger`, Cron mit dem Unschedule-if-exists-Guard aus `20260925010000_codex_build_retention.sql:63-67`. **Nie** `create extension pg_cron` wiederholen; das hat am 2026-09-25 den ersten `db push` zurückgerollt.
- Bei Rechten auf Funktionen gilt: Supabase gibt `anon` und `authenticated` per Default-Privileg EXECUTE auf alles Neue in `public`. Deshalb immer `revoke all on function … from public, anon, authenticated;` vor dem gezielten `grant`.
- Reihenfolge der Zeitstempel: `supabase db push` verweigert eine lokale Migration, die älter ist als die zuletzt angewandte. Liegt ein anderer Plan (z. B. D02) schon angewandt vor dir, benennst du deine noch nicht angewandte Datei vor dem Push auf einen neuen Zeitstempel um.

### Schritt 4 — Migration: Bucket privat, gezielte Lese-Policy (AUD-115, AUD-351)

Datei: neu, `npm run db:migration:new -- feedback_images_private` → `supabase/migrations/<ts>_feedback_images_private.sql`. Kopf nach B3; im WHY auf `20260726170000_user_feedback_channel.sql:37-43` („KNOWN, PRE-EXISTING GAP“) verweisen.

Inhalt (Skizze):
```sql
update storage.buckets set public = false where id = 'feedback-images';
drop policy if exists "feedback_images_public_read" on storage.objects;

-- Who may read one object: its uploader, any admin, or the author of a USER
-- topic whose author-channel messages reference it (admin replies with a
-- screenshot). SECURITY DEFINER so the policy can probe
-- feedback_author_messages without granting the caller read access to it.
create or replace function public.can_read_feedback_image(p_name text)
returns boolean
language sql stable security definer set search_path = ''
as $$
  select (storage.foldername(p_name))[1] = auth.uid()::text
      or public.is_admin()
      or exists (
           select 1 from public.feedback_author_messages m
           where public.owns_feedback(m.feedback_id)
             and strpos(m.body, p_name) > 0
         );
$$;
revoke all on function public.can_read_feedback_image(text) from public, anon, authenticated;
grant execute on function public.can_read_feedback_image(text) to authenticated;

drop policy if exists "feedback_images_scoped_read" on storage.objects;
create policy "feedback_images_scoped_read" on storage.objects
  for select to authenticated
  using (bucket_id = 'feedback-images' and public.can_read_feedback_image(name));
```

- Upload- und Delete-Policies (`feedback_images_owner_upload` aus `20260904040000`, `feedback_images_owner_delete`) sowie die restriktiven Approval-Gates für INSERT/DELETE aus `20260805120000_email_allowlist.sql:265-273` bleiben unverändert.

### Schritt 7 — Migration: Profil-Anlage und `is_admin(uuid)` (AUD-318, AUD-317)

Datei: neu, `npm run db:migration:new -- profile_insert_and_is_admin_grants` → `supabase/migrations/<ts>_profile_insert_and_is_admin_grants.sql`. Kopf nach B3.

Inhalt (Skizze):
```sql
-- AUD-318: the only INSERT path a session has into profiles is its own row
-- with neutral viewer values. handle_new_user() (SECURITY DEFINER) and the
-- service role are unaffected (they bypass RLS).
drop policy if exists "profiles_self_upsert" on public.profiles;
drop policy if exists "profiles_self_insert" on public.profiles;
create policy "profiles_self_insert" on public.profiles
  for insert to authenticated
  with check (
    auth.uid() = id
    and role = 'viewer'
    and is_approved = false
    and suspended_at is null and suspended_until is null and suspension_reason is null
    and last_seen_at is null
    and username is null
  );

-- AUD-317: the api_tokens policy is the only caller of is_admin(uuid) that
-- runs as `authenticated` — move it to the no-arg is_admin() FIRST, otherwise
-- the revoke below breaks token management for admins.
drop policy if exists "admins manage own tokens" on public.api_tokens;
create policy "admins manage own tokens" on public.api_tokens
  for all to authenticated
  using (owner_user_id = auth.uid() and public.is_admin())
  with check (owner_user_id = auth.uid() and public.is_admin());

revoke execute on function public.is_admin(uuid) from public, anon, authenticated;
grant execute on function public.is_admin(uuid) to service_role;
```

Hinweise:
- Warum die Reihenfolge wichtig ist: Funktionen in RLS-Policies laufen mit den Rechten der aufrufenden Rolle. Der Audit-Fix-Satz „policies run as the table owner“ stimmt hier nicht. `20260529_public_api_tokens.sql:73-76` ruft `is_admin(auth.uid())` als `authenticated` auf.
- `username` muss null sein, weil nur `set_username()` Handles prüft. Gibt es inzwischen weitere privilegierte Spalten (Vorab prüfen 5), kommen sie in die WITH-CHECK-Liste.
- ROLLBACK: alte Policy aus `00001_init_schema.sql:20-21`, alte API-Token-Policy aus `20260529_public_api_tokens.sql:73-76`, `grant execute on function public.is_admin(uuid) to authenticated, anon;`.
