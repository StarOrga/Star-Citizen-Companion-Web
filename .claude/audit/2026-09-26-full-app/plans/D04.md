## Ziel und Definition of Done

- Jeder Pull Request und jeder Push auf `main` startet den Workflow `.github/workflows/web-ci.yml`. Er prüft: `npm ci`, `npm run typecheck`, `npm run lint`, `npm run test:gate`, `npm run test:assets-worker`, `npm test` (Karma, ChromeHeadless), `npm run build`, `npm run gate:mobile` gegen das gebaute `dist/`.
- Ein PR, der nichts an der Web-App ändert, bekommt trotzdem grüne Checks, weil die schweren Jobs dann übersprungen werden (Skip zählt als Erfolg). So kann der Owner die Checks als „required“ markieren, ohne dass reine Doku-PRs hängen.
- `package.json` hat `engines.node`, im Repo liegt `.nvmrc` mit `24`. Die README nennt die Node-Version.
- `node scripts/mobile-gate.mjs --selftest` läuft als root in einem Linux-Container mit Playwright-Chromium grün, ohne `CHROME_BIN`. Scheitert der Browserstart, zeigt die Fehlermeldung die letzten stderr-Zeilen von Chrome.
- `npm run test:functions` führt alle `supabase/functions/**/*.test.{ts,mjs}` unter Node aus. Die bisher Deno-only-Datei `ship-link/_rsi-url.test.ts` läuft jetzt auch unter Node.
- `.github/workflows/edge-functions-deploy.yml` führt im `plan`-Job die Funktions-Tests unter Node **und** Deno aus. Ein roter Test stoppt den Deploy, weil `deploy` `needs: plan` hat.
- `npm run lint` ist ein echtes `ng lint` (angular-eslint, Flat Config) und endet mit Exit 0 (0 Errors; Warnungen erlaubt und dokumentiert).
- Doku ist nachgezogen: `CLAUDE.md` (Commands), `README.md`, `docs/mobile-gate.md`, `docs/feedback-routine.md`, `.claude/skills/ship/SKILL.md`.

### Schritt 5 — Workflow `web-ci` (AUD-101, AUD-112, AUD-343)

Datei: neu `.github/workflows/web-ci.yml`.

Aufbau (Actions-Majors wie in den vorhandenen Workflows: `actions/checkout@v7`, `actions/setup-node@v7`, `actions/upload-artifact@v7`). Die Jobs `checks`, `unit` und `build-and-mobile-gate` sind unten **verkürzt** notiert (`steps: […]`). Im echten YAML wird jeder Eintrag ein eigener `- uses:`- bzw. `- run:`-Schritt, die zwei Gate-Schritte mit ihrem `if:`, der Upload mit `if: failure()`:

```yaml
name: web-ci

# Why: nothing checked the Angular app on a PR; a red suite could merge and
# Vercel would deploy it (audit 2026-09-26, AUD-101/112/343).
on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: web-ci-${{ github.ref }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

jobs:
  changes:            # decides whether the web app is touched at all
    name: does this touch the web app
    runs-on: ubuntu-latest
    timeout-minutes: 5
    outputs:
      web: ${{ steps.diff.outputs.web }}
    steps:
      - uses: actions/checkout@v7
        with: { fetch-depth: 0 }
      - id: diff
        env:
          EVENT: ${{ github.event_name }}
          PR_BASE_SHA: ${{ github.event.pull_request.base.sha }}
          PUSH_BEFORE: ${{ github.event.before }}
        run: |
          set -euo pipefail
          if [ "$EVENT" = "workflow_dispatch" ]; then
            echo "web=true" >> "$GITHUB_OUTPUT"; exit 0
          fi
          # same base resolution as edge-functions-deploy.yml (plan job)
          case "$EVENT" in
            pull_request) BASE="$PR_BASE_SHA" ;;
            *)            BASE="${PUSH_BEFORE:-}" ;;
          esac
          if [ -z "$BASE" ] || [ "$BASE" = "0000000000000000000000000000000000000000" ]; then
            BASE="$(git rev-parse HEAD^)"
          fi
          WEB_RE='^(src/|public/|scripts/|cloudflare/assets-worker/|supabase/functions/ingest-skins/|\.claude/hooks/|package\.json$|package-lock\.json$|angular\.json$|tsconfig[^/]*\.json$|ngsw-config\.json$|vercel\.json$|\.nvmrc$|eslint\.config\.[cm]?js$|CHANGELOG\.md$|\.github/workflows/web-ci\.yml$)'
          # No `grep -q`: with pipefail an early grep exit SIGPIPEs git diff (141)
          # and a real match would read as "false".
          if git diff --name-only "$BASE" HEAD | grep -E "$WEB_RE" > /dev/null; then WEB=true; else WEB=false; fi
          echo "web=$WEB" >> "$GITHUB_OUTPUT"
          echo "web-app touched: $WEB (base $BASE)"

  checks:
    name: typecheck · lint · gate scripts · worker tests
    needs: changes
    if: needs.changes.outputs.web == 'true'
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps: [checkout, setup-node (node-version-file: .nvmrc, cache: npm), npm ci,
            npm run typecheck, npm run lint, npm run test:gate, npm run test:assets-worker]

  unit:
    name: unit tests (Karma)
    needs: changes
    if: needs.changes.outputs.web == 'true'
    runs-on: ubuntu-latest
    timeout-minutes: 30
    steps: [checkout, setup-node, npm ci, npm test]

  build-and-mobile-gate:
    name: production build + mobile gate
    needs: changes
    if: needs.changes.outputs.web == 'true'
    runs-on: ubuntu-latest
    timeout-minutes: 30
    env:
      SC_TEST_EMAIL: ${{ secrets.SC_TEST_EMAIL }}
```

Einzelheiten:
- **Warum ein `changes`-Job statt `paths:`?** Ein Workflow, den ein Pfadfilter gar nicht startet, meldet nie einen Status. Als „required check“ bliebe jeder Doku-PR für immer auf „Expected — waiting“. Ein per `if:` übersprungener Job zählt dagegen als erfüllt.
- `changes` setzt `web=true`, wenn eine geänderte Datei auf diesen Regex passt, sonst `false`. Bei `workflow_dispatch` immer `true`:
  `^(src/|public/|scripts/|cloudflare/assets-worker/|supabase/functions/ingest-skins/|\.claude/hooks/|package\.json$|package-lock\.json$|angular\.json$|tsconfig[^/]*\.json$|ngsw-config\.json$|vercel\.json$|\.nvmrc$|eslint\.config\.[cm]?js$|CHANGELOG\.md$|\.github/workflows/web-ci\.yml$)`
  - `CHANGELOG.md` gehört dazu, weil `prebuild` daraus `scripts/gen-release-notes.js` erzeugt.
  - `.claude/hooks/` gehört dazu, weil `test:gate` den Hook-Test enthält.
  - Bekannte Lücke, bewusst hingenommen: `scripts/check-no-personal-emails.mjs` (im `prebuild`) prüft **alle** getrackten Dateien (`git ls-files`). Ein reiner Doku-PR mit einer privaten Mailadresse überspringt `web-ci`, fällt aber im Vercel-Preview-Build auf, der auf jedem PR läuft. Nicht die Regex auf „alles“ erweitern, sonst verliert der `changes`-Job seinen Zweck.
  - Die Basis wie im `plan`-Job von `edge-functions-deploy.yml` bestimmen (PR → `base.sha`, Push → `before`, Null-SHA → `HEAD^`), dann `git diff --name-only "$BASE" HEAD`.
- Jeder Befehl ist ein eigener `- run:`-Schritt, damit im Log sofort sichtbar ist, was rot ist.
- Karma: `npm test` ist `ng test --watch=false --browsers=ChromeHeadless`. `ubuntu-latest` bringt Google Chrome mit. Scheitert der Start mit „No usable sandbox“ (AppArmor auf Ubuntu 24.04), gibt es zwei Auswege:

  - (b) eine eigene Karma-Konfiguration mit Custom-Launcher `ChromeHeadlessCI` (`base: 'ChromeHeadless'`, `flags: ['--no-sandbox']`), und in der CI `npm test -- --browsers=ChromeHeadlessCI`. Heute gibt es keine `karma.conf.*` (der Builder `@angular/build:karma` nutzt seine eingebaute). Deshalb nicht von Hand schreiben, sondern `npx ng generate config karma` erzeugen lassen (legt `karma.conf.js` an und trägt `karmaConfig` in `angular.json` → `projects.sc-companion.architect.test.options` ein). Wegen `"type": "module"` die Datei in `karma.conf.cjs` umbenennen und den Pfad in `angular.json` nachziehen, dann nur `customLaunchers` ergänzen.

  (a) zuerst probieren, das lässt die lokale Konfiguration unberührt.

## Manuelle Schritte (nur der Owner)

1. **Checks als Pflicht markieren** (nach dem ersten grünen Lauf, sonst sind die Namen nicht auswählbar):
   - GitHub → Repository → Settings → Rules → Rulesets, Regel für `main` (oder Branches → Branch protection rule).
   - „Require status checks to pass“ mit diesen vier Checks: `does this touch the web app`, `typecheck · lint · gate scripts · worker tests`, `unit tests (Karma)`, `production build + mobile gate`. Optional zusätzlich `which functions does this touch` aus `edge-functions`.
   - Erst damit blockiert ein roter Lauf den Merge. Vercel deployt `main` weiterhin unabhängig davon.
2. **Angemeldeter Gate-Durchlauf in der CI (Entscheidung):** Das Testkonto ist Admin auf Produktionsdaten, und „Sign-out is global“ (`.claude/deep-knowledge/test-account.md`). Empfehlung: vorerst **nicht** setzen, oder ein eigenes, nur freigeschaltetes Nicht-Admin-Konto anlegen. Falls gewünscht:
   ```
   gh secret set SC_TEST_EMAIL
   gh secret set SC_TEST_PASSWORD
   ```
   Ohne Secrets läuft der öffentliche Durchlauf, und der Report listet die angemeldeten Routen als ungeprüft.
3. **Vercel-Node-Version kontrollieren:** Im Preview-Deployment des PRs → Build Logs nach „Node.js“ suchen. Erwartet 24.x. Steht dort 22.x, im Vercel-Projekt unter Settings → Build and Deployment → Node.js Version 24.x lassen und die Spanne in `engines` auf `^24.15.0` verengen.
4. **Actions-Minuten:** Ist das Repo privat, verbrauchen die drei Jobs pro Web-PR grob 10–15 Minuten. Im Billing-Tab der Organisation einmal nachsehen, ob das ins Kontingent passt. Ist es öffentlich, entfällt der Punkt.
