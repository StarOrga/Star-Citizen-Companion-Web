## Ziel und Definition of Done

- Eine hängende PostgREST-Lese-Anfrage endet nach spätestens 20 s. Der Leser zeigt dann seine Fehlerkarte mit „Das hat zu lange gedauert.“ (`errors.timeout` aus D05) und Retry, statt endlos zu drehen.
  - Das gilt für den Hangar (`loadAll`), jeden Codex-Leser, die Keybinds, die Set-Seite, Admin-Listen und alle anderen `.select()`-Reads.
  - postgrest-js wiederholt einen Timeout nicht. Die Frist ist also 20 s, nicht ~70 s.
- Schreibende PostgREST-Anfragen (`POST`/`PATCH`/`DELETE`, schreibende RPCs) laufen unverändert ohne Frist.
- Token-Liste (`/admin/api-tokens`) und Konzeptseite (`/konzept/:id` bzw. `/concept/:id`) bleiben nicht mehr ewig auf „lädt“. Nach 20 s zeigen sie ihren vorhandenen Fehlerzustand.
- Beim Wechsel des Schiffs im Skin-Viewer wird der laufende GLB-Kopf-Read abgebrochen. Ein hängender Read endet nach 10 s.
- Liefert `getSession()` einen Fehler oder hängt es, bleibt keine Navigation mehr auf dem Boot-Splash stehen. Nach spätestens 10 s gilt der Besuch als abgemeldet und die Guards entscheiden. Alle fünf Guards warten über ein gemeinsames `AuthService.whenReady()` statt mit fünf eigenen 30-ms-Polls.
- Ein seit Stunden offener Codex-Tab bemerkt beim Zurückkehren einen neuen LIVE-Build:
  - Wer „live“ gelesen hat, wird auf den neuen Build gehoben. Die Listen laden neu, die Patch-Zeile sagt es einmal („Katalog aktualisiert auf Patch …“).
  - Wer bewusst einen alten Patch liest, bleibt dort. `viewingPastPatch()` stimmt jetzt, die Ausrüst-Sperre (REQ-10) greift.
  - Ist sein Build gelöscht worden, landet er auf dem neuen LIVE-Build statt vor leeren Listen.
- Die Einordnung auf der Set-Seite zeigt bei einem Fehler oder Timeout der RPC einen Fehlerzustand mit „Erneut versuchen“. Ein Statement-Timeout (kalter Cache) wird einmal automatisch wiederholt.
- Verliert das Board-Figure-Canvas den WebGL-Kontext, erscheint wieder die gezeichnete Figur (SVG-Fallback) statt einer leeren Fläche. Kommt der Kontext zurück, startet die 3D-Figur neu.
- Die installierte App startet offline mit Texten statt Rohschlüsseln: `/i18n/*.json`, `/meshopt/**` und `/release-notes.json` stehen nach dem ersten Abruf im Service-Worker-Cache.
- Gates grün: `npm run typecheck`, `npm test`, `npm run build`, `npm run test:gate`.

- Neue Datei `src/app/core/deadline.ts`:
  ```ts
  export const READ_TIMEOUT_MS = 20_000;
  /**
   * Read-only RPCs the client calls — checked against supabase/migrations on 1b08612.
   * All `stable` except get_telemetry_stats (declared volatile, body is SELECT-only).
   * NOT here: hangar_follow_snapshot — it writes the follower's sync copy.
   */
  export const READ_RPCS: ReadonlySet<string> = new Set([
    'codex_facet_values', 'codex_compatible_items', 'codex_armor_rating',
    'get_shared_loadout', 'peek_shared_loadout',
    'list_loadouts_shared_with_me', 'list_loadout_shares', 'list_my_friend_edges',
    'my_account_status', 'my_desktop_connections',
    'starscape_vote_state', 'starscape_top_wallpapers', 'starscape_release_for_channel',
    'starscape_latest_release', 'desktop_release_for_channel',
    'get_telemetry_stats', 'list_users_for_admin', 'list_reports_for_admin',
    'list_allowed_emails', 'pending_access_requests', 'list_p4k_bundles_for_collaborator',
    'find_user_by_username',
  ]);
  export function isReadRequest(method: string, url: string, restBase: string): boolean;
  export function createReadDeadlineFetch(restBase: string, ms?: number, base?: typeof fetch): typeof fetch;
  export function deadlineSignal(ms?: number, outer?: AbortSignal | null): AbortSignal;
  ```
- `isReadRequest` liefert `true` für `GET`/`HEAD` unter `restBase` sowie für `POST ${restBase}rpc/<name>` mit `<name>` in `READ_RPCS` (Query-String vor dem Vergleich abschneiden). Sonst liefert es `false`. Die Normalisierung macht der Wrapper: `input` kann `string`, `URL` oder `Request` sein, daraus wird `url = typeof input === 'string' ? input : input instanceof URL ? input.href : input.url` und `method = (init?.method ?? (input instanceof Request ? input.method : 'GET')).toUpperCase()`. supabase-js ruft am `1b08612` mit einem URL-String plus `init` auf.
- `createReadDeadlineFetch(...)` gibt `(input, init) => …` zurück:
  - Ist die Anfrage kein Read, reicht der Wrapper unverändert an `base` durch. `base` ist standardmäßig `(...a) => fetch(...a)`, gebunden, sonst gibt es „Illegal invocation“.
  - Ist sie ein Read:
    ```ts
    const ctrl = new AbortController();
    const timer = AbortSignal.timeout(ms);
    timer.addEventListener('abort', () =>
      ctrl.abort(new DOMException(`TimeoutError: read deadline ${ms} ms exceeded`, 'AbortError')), { once: true });
    init?.signal?.addEventListener('abort', () => ctrl.abort(init.signal!.reason), { once: true });
    if (init?.signal?.aborted) ctrl.abort(init.signal.reason);
    return base(input, { ...init, signal: ctrl.signal });
    ```
  - **Warum `AbortError` als Name:** postgrest-js 2.117 (`fetchWithRetry`) wiederholt `GET`/`HEAD` bei jeder Ablehnung, die kein `AbortError` ist, bis zu 3-mal mit 1/2/4 s Backoff. Eine `TimeoutError`-Ablehnung würde die Frist auf ~70 s strecken. Ein `AbortError` wird sofort als Ergebnis `{ error: { message: 'AbortError: TimeoutError: read deadline 20000 ms exceeded', code: '' } }` durchgereicht. D05s `describeError` erkennt `TimeoutError` im Text und liefert `errors.timeout`.
  - **Warum `AbortSignal.timeout` statt `setTimeout`:** Es erzeugt keinen Zone-Macrotask. Eine Frist pro Read würde die NgZone sonst 20 s lang instabil halten, das stört `registerWhenStable` des Service Workers und `fixture.whenStable()` in Specs.
  - Den Timer **nicht** beim Eintreffen der Header aufheben. Die Frist deckt so auch einen stockenden Body ab. Ein Abbruch nach vollständigem Lesen hat keine Wirkung.
- `deadlineSignal(ms = READ_TIMEOUT_MS, outer)` ist für eigene `fetch`-Aufrufe gedacht. Es liefert `AbortSignal.any([outer, AbortSignal.timeout(ms)])`, wenn `outer` gesetzt ist. `AbortSignal.any` gibt es in Chrome 116, Safari 17.4 und Firefox 124. Existiert es nicht, verknüpft die Funktion die Signale per Listener wie oben.
- Neue Spec `src/app/core/deadline.spec.ts`:
  - Klassifikations-Tabelle für `isReadRequest`: GET-Tabelle ja, HEAD ja, POST-Tabelle nein, PATCH nein, `rpc/codex_armor_rating` ja, `rpc/set_user_role` nein, `rpc/hangar_follow_snapshot` nein (schreibt), fremde URL nein, `/auth/v1/token` nein.
  - `READ_RPCS.size` ist 22 (fängt ein versehentliches Wiederaufnehmen ab). **Ist D14 zuerst gemergt**, ruft die App zusätzlich `rpc('admin_feedback_board_delta')` auf (D14 Schritt 5: `STABLE`, `SECURITY INVOKER`, nur lesend).   - Ein `base`, das nie auflöst, aber auf `signal.abort` mit `signal.reason` ablehnt. Mit `ms = 30` lehnt der Wrapper nach ~30 ms mit `name === 'AbortError'` ab, die Nachricht enthält `TimeoutError`. Echte Zeit, weil `AbortSignal.timeout` nicht an Jasmine-Clock hängt.
  - Ein Write wird ohne neues Signal durchgereicht.
  - Ein Abbruch durch den Aufrufer kommt mit dessen `reason` an.

#### Schritt 7 · WebGL-Kontextverlust der Board-Figur abfangen (AUD-019)

- `src/app/codex/codex-board-figure.component.ts`:
  - Neue private Felder: `contextLost = false`, `destroyed = false`, `detachLost: (() => void) | null = null`, `detachRestored: (() => void) | null = null`.
  - Zwei getrennte Abmelder, weil der `restored`-Listener einen **natürlichen** Verlust überleben muss. Würde `teardown()` beim Verlust beide Listener abhängen, käme das `webglcontextrestored` nie mehr an und die 3D-Figur nie zurück.
  - In `boot()` direkt nach `new T.WebGLRenderer(...)`:
    ```ts
    const onLost = (e: Event) => {
      e.preventDefault(); // ohne preventDefault stellt der Browser den Kontext nie wieder her
      if (this.renderer !== renderer) return;
      this.contextLost = true;
      this.teardown(); // hängt nur den lost-Listener ab, der restored-Listener bleibt
    };
    const onRestored = () => {
      if (!this.contextLost || this.destroyed) return;
      this.contextLost = false;
      this.detachRestored?.(); this.detachRestored = null; // boot() meldet frische Listener an
      void this.boot();
    };
    canvas.addEventListener('webglcontextlost', onLost);
    canvas.addEventListener('webglcontextrestored', onRestored);
    this.detachLost = () => canvas.removeEventListener('webglcontextlost', onLost);
    this.detachRestored = () => canvas.removeEventListener('webglcontextrestored', onRestored);
    ```
  - `teardown()` ruft als **Erstes** `this.detachLost?.(); this.detachLost = null;`, **vor** `this.renderer?.forceContextLoss()`. `forceContextLoss` löst selbst ein `webglcontextlost` aus, das darf nicht wieder in `teardown` laufen. `forceContextLoss()` nur rufen, wenn der Kontext noch lebt: `if (!this.renderer?.getContext().isContextLost()) this.renderer?.forceContextLoss();`. Beim natürlichen Verlust ist der Kontext schon verloren, ein zweites `loseContext` würde nur eine GL-Warnung erzeugen.
  - Im `destroyRef.onDestroy` vor `teardown()`: `this.destroyed = true; this.detachRestored?.(); this.detachRestored = null;`. So startet ein spätes `restored` nichts mehr.
  - Das `catch` in `boot()` („No engine, no problem“) ruft weiter `teardown()`; ein dort evtl. noch angemeldeter `restored`-Listener ist wegen `contextLost === false` wirkungslos.
  - `teardown()` setzt `ready` auf `false`. Damit zeigt `.board-stage.on ~ .board-doll` wieder die SVG-Figur, und die Anker nutzen die 2D-Positionen.
- Spec `src/app/codex/codex-board-figure.component.spec.ts`: neuer Fall. Sobald `ready()` wahr ist (oder die Engine in ChromeHeadless fehlt, dann `pending()`), auf dem Canvas `new Event('webglcontextlost', { cancelable: true })` dispatchen. Danach ist `ready()` `false`, `.board-doll` sichtbar und das Event `defaultPrevented`. Zweiter Fall: Nach dem Verlust löst `new Event('webglcontextrestored')` einen neuen `boot()` aus (`spyOn<any>(component, 'boot')`, die Methode ist privat). Dritter Fall: Destroy nach dem Verlust, dann `webglcontextrestored`, und `boot` wird nicht gerufen.
- Prüfen im Browser: Set-Seite öffnen, in der Konsole `document.querySelector('sc-codex-board-figure canvas').getContext('webgl2').getExtension('WEBGL_lose_context').loseContext()`. Die gezeichnete Figur erscheint. `…restoreContext()` bringt die 3D-Figur zurück.
