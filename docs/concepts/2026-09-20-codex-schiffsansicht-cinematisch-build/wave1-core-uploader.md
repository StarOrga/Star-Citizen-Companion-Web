# Wave 1 — core-uploader: silhouette extraction + catalog phase

Branch: `claude/codex-schiffsansicht-design-d0ab3a-core-uploader` (off
`claude/codex-schiffsansicht-design-d0ab3a`). Owns `data-uploader/**` only —
`supabase/**` and `src/app/**` are core-web's (Wave 1, parallel).

## What was built

1. **`data-uploader/python/sc_extract/silhouette.py`** — pure, dependency-free
   (numpy + stdlib only, no opencv) geometry pipeline: project triangles
   top-down → rasterise to a boolean mask → morphological denoise (close+open)
   → Moore-neighbour contour trace (outer + holes ≥ area threshold) → Chaikin
   smooth → Douglas-Peucker simplify (metres tolerance) → normalise into the
   shared `0..1000` viewBox, nose up. Also `project_anchors()` (reuses the
   SAME `x=(X-min)/span`, `y=1-(Y-min)/span` projection as the web 2D hull map,
   `hardpoint-map.ts` `projectHardpoint`) and `build_entity_silhouette()` /
   `build_silhouette()` that assemble the wave-0 §C1 contract row.
2. **`data-uploader/python/sc_extract/silhouette_export.py`** — the P4K /
   cgf-converter wiring: converts one mesh to a raw (untextured — a silhouette
   needs no material) glb via the same `cgf-converter -glb -objectdir` call
   `hull3d.py` uses, un-rigs it (`glb_materials.strip_noop_skins`, defect A —
   without this a multi-part hull collapses to the origin and the silhouette
   would be wrong), walks the node hierarchy to world-space triangles
   (`world_triangles_from_glb`), and hands them to `silhouette.py`. Caches the
   `silhouette` sub-object (the expensive geometry, not the cheap per-entity
   anchors) under `<out_dir>/silhouette_cache/<sha256(mesh bytes)>-<tool_version>.json`.
3. **`data-uploader/python/sc_extract/silhouette_build.py`** — CLI driver, the
   sibling cached step to `ship_export.py` (the 3D-hull/skin build), but
   generic over kind. Reads `silhouettes/_build_manifest.json` (see below),
   deduplicates by mesh path (a ship's hull is one conversion regardless of
   how many editions share it), and writes one row per entity to
   `<out>/silhouettes/rows/<kind>__<class_name>.json`.
4. **`dataforge_extract.py`** changes: `_note_silhouette_candidate()` records
   every ship / weapon / component / armor item whose mesh resolves (via the
   existing generic `_hull_path()` — unchanged, it already falls back to any
   `.cga`/`.cgf` path on any component, so it needed no new mesh-discovery
   logic); `_write_silhouette_manifest()` (called from `run()`, mirrors
   `_write_skin_build_manifest`) writes `silhouettes/_build_manifest.json =
   {"entities": [{"kind","class_name","mesh"}, ...]}`.
5. **`data-uploader/src/lib/catalog-map.ts`** — `SilhouetteRow` +
   `mapSilhouettes()`: maps a `silhouettes/rows/*.json` contract file onto the
   pinned columns the task specified (build identity, `kind`, `class_name`,
   `view_box`, `path`, `bbox`, `anchors`, `unresolved`, `meta`,
   `generated_at`). `meta` jsonb carries the audit-trail fields that are not
   query surface: `schema`, `toolVersion`, `source`, `noseUp`,
   `scaleMPerUnit`, `pointCount`, `simplifyToleranceM`.
6. **`data-uploader/src/lib/catalog-phases.ts`** — new phase
   `codex_silhouettes`, inserted between `codex_item_ports` and
   `codex_locale_strings` (fixed order both the live bar and the resume banner
   read off; `CATALOG_PHASE_TOTAL` is now 16, was 15).
7. **`data-uploader/src/main/catalog-bridge.ts`** — step 8b: reads
   `outDir/silhouettes/rows/*.json` (rows live in a `rows/` subdirectory,
   sibling to `_build_manifest.json`, so a directory-wide JSON read never picks
   up the manifest as a row), sends `clear_silhouettes` once at the start of
   the phase (same resumable guard as `clear_ports` — only on `skip === 0`),
   then `silhouettes` in chunks of 500 — byte-for-byte the same shape/batching
   `ports`/`clear_ports` already use.

## Entity kinds

- **ship** — every ship/vehicle whose hull `.cga` resolves via the existing
  `_hull_path()` (unchanged code path already used for dimensions/hardpoints).
  Gets `anchors[]` + `unresolved[]` from the SAME `hardpointTransforms` /
  `hardpointFrame` the extractor already resolved for that ship (read back out
  of `ships/<class>.json` by `silhouette_build.py`, not re-derived).
- **weapon**, **component** — every entity with a resolvable mesh path,
  silhouette only (no anchors — the contract reserves `anchors`/`unresolved`
  for ships, per wave-0 §C1).
- **armor** — items gated the same way `_project_item()` already gates the
  armor stat block: `AttachDef.Type` in the FPS armor vocabulary OR
  `SCItemVehicleArmorParams` present. Other item kinds (consumables, tools,
  ...) are NOT candidates — out of the literal "weapons, components and armor
  items" scope.
- **Not candidates**: any entity whose mesh path does not resolve (no
  `_hull_path()` hit) — never listed in the manifest, never gets a row, so the
  website's "ohne Geometrie" fallback (wave-0 §C3) is correct by construction.

## Cache key

`silhouette_cache/<sha256(mesh bytes)>-<tool_version>.json`, holding the
`silhouette` sub-object only (the geometry — the expensive cgf-converter
round trip). Anchors are re-derived fresh every run (cheap, pure Python, and
they depend on the ship's OWN hardpoint transforms, not the mesh hash, so
caching them separately would risk staleness). A ship's hull is shared by
every livery/edition and an item's mesh by every variant pointing at the same
`.cga`/`.cgf`, so `silhouette_build.py` also dedupes by mesh path up front —
one cgf-converter subprocess per distinct mesh, not per entity.

## Runtime per ship

**Not measured** — this worktree has neither the live `Data.p4k`
(`sc-data-p4k-location` memory names a path on a different machine/session)
nor a fetched `cgf-converter` binary (`tools/fetch_tools.py`), so
`silhouette_build.py` was never run end-to-end against real data. Expect it to
track `hull3d.py`'s per-skin cgf-converter cost roughly 1:1 (same conversion
call, no texture/material step) minus the `gltf-transform optimize` pass this
module never runs — so noticeably CHEAPER per mesh than a skin build, but
still one external process per distinct mesh. The rasterise→trace→simplify
pipeline itself is pure Python/numpy and negligible next to the subprocess
cost (a synthetic 2-triangle mesh through the full pipeline is well under
10 ms; a real multi-thousand-triangle hull will be dominated by the
triangle-rasterisation loop, still expected to be well under a second).

## Dependencies added

None. `numpy` and `Pillow` were already uploader dependencies (numpy is a hard
`scdatatools` transitive dependency; see `requirements.txt`). The contour
tracer is pure Python specifically to avoid adding opencv, which has no other
consumer in this codebase and is a large native wheel — documented in
`silhouette.py`'s module docstring.

## Questions for the user

1. **Live run against `Data.p4k` + `cgf-converter`** was not possible in this
   worktree (neither is present here) — the contract row above is synthetic,
   not extracted from a real ship. Someone with the live archive + fetched
   tools should run `python -m sc_extract.silhouette_build --p4k <path> --out
   <extractor out_dir> --converter <path> --tool-version <ver> --build-json
   '{"channel":"LIVE","patchVersion":"...","buildNumber":"..."}'` once against
   a real extract (Cutlass Black is the usual verified anchor) to confirm the
   raster/trace/simplify constants (`MASK_SIZE=1024`, `MIN_HOLE_AREA_PX=24`,
   `DEFAULT_SIMPLIFY_TOLERANCE_M=0.15`, `CHAIKIN_ITERATIONS=2`) actually
   produce a recognisable, SCC-styled outline on real geometry — they are
   reasoned defaults, not tuned against a real hull.
2. **DONE** — see "Nachtrag" below: the desktop app now runs the silhouette
   build itself as part of the guided flow (main-process bridge + renderer
   step), the same way it already runs the 3D-skin build.
3. **Armor's mesh source**: the task said "find where their meshes are located
   — if items have no mesh path in the current extract, say so". Reusing the
   existing generic `_hull_path()` fallback (`_find_geometry_path`, already
   walks any component for a `.cga`/`.cgf` path) turned out to cover it without
   new discovery code, but this was NOT verified against a live extract (see
   Q1) — an armor piece whose geometry lives somewhere `_find_geometry_path`'s
   8-level-deep generic walk does not reach would silently get no silhouette
   (never a placeholder, per the "nothing invented" rule) rather than an error
   surfaced anywhere. Worth spot-checking once Q1 is run.
