# Round 2 brief — target design: app shell per page type (SC Companion)

Locale: de (all page text German). Concept mode: mixed. Round 1 was a `free` analysis round
(frozen, `rounds/01.html`; read it for the facts, numbers and wording — it is the evidence base).

## What this round is

Round 2 is the **target design concept**: `data-iteration-template="design"`,
`data-design-set="alternatives"`, **3 clearly (even excessively) different design directions**
for ONE coherent app-shell system: global header, subheader, footer, page widths/spacing and
page navigation across four page types (+ a "plain/auth" flavour). Declare
`data-viewports` with desktop, tablet and phone (the user explicitly demands that tablet and
phone are first-class: "top tablet und mobile fit, ein Genuss, frische Innovation, keine
unübersichtliche und keine lahme alte Seite — die muss bangen!").

Visual identity to respect: SC Companion is a dark Star Citizen companion PWA. Tokens: dark
space background, accent cyan/blue (`--sc-accent`), `--sc-accent-hot` red ONLY for admin /
elevated-access surfaces, `--sc-warning` amber for worse comparison values, `--sc-danger` only for
errors/destructive. Brand: logo + wordmark "SC Companion" with a small handwritten "alpha" badge.
Main nav: Verse · Codex · HQ (+ Admin in red for admins). Real content to use in mocks (no
lorem ipsum): Verse briefing (planet/star sky, current patch "4.3.x", next patch countdown,
news headlines), ship detail "Aegis Avenger Stalker" (specs table, components, weapons
hardpoints), Codex index (ship list with filters: manufacturer, size, role; ~260 ships),
weapon swap overlay (choose a weapon for a hardpoint: S3 ballistic cannons with DPS/alpha/range),
global search results grouped (Ships, Weapons, Items, News, Gallery images), HQ hangar
(owned ships, loadouts), gallery lightbox (Starscape wallpaper image), patch dossier 4.3.1.

Every design shows the SAME set of screens so the user can compare (a screen = a logical state):

1. **Cinematic hub** — `/verse` briefing: full-bleed stage starting at y=0 BEHIND a transparent
   header (scrim), header turns solid when scrolled and hides on scroll-down / reveals on
   scroll-up; NO subheader; minimal one-line footer strip at document end (one-pager). Show both
   states: at top and scrolled (header revealed solid).
2. **Content page** — ship detail (Avenger Stalker): NARROW focused column (user loves narrow
   for info-heavy pages: "zwingt zum Fokus"), breadcrumb bar (Codex › Schiffe › Aegis › Avenger
   Stalker), subheader with integrated search field, anchor/section nav for the long sheet,
   compact footer at the very end.
3. **Tool page** — Codex index: full width, subheader = slim title + integrated search + sticky
   toolbar (local filters as chips, sort, view toggle, 1 primary action); header behaviour per
   P1 (compact, persistent on tool pages).
4. **Search in action** — the search lives in the SUBHEADER (see user notes below), focused
   state with animated transformation, results grouped and ranked by context, each result with up
   to 3 quick-action icons + 1 button action, hotkey hint shown in the field when unfocused, and
   the "Companion fragen" offer once the query has more than 3 words.
5. **Popup-detail** — weapon swap overlay on the ship page: no back bar, an ✕, fixed responsive
   takeover of the screen (desktop: large centred sheet; tablet: side/bottom sheet; phone: full
   screen), has its own URL. Must make the weapon choice shine (comparison, filters, the
   potential the user sees there).
6. **Phone** — the content page and the cinematic hub on the phone (bottom-reachable nav,
   one-line auto-hiding header instead of today's 177 px two-row header, compact footer ≤120 px,
   FAB lane respected), plus the **"Auf dem Handy weitermachen"** icon/popup (see below).

Each design also shows (on whichever screen fits) the **Beta switch as a small overlay bottom-left,
visible ONLY for admins and collaborators** (user: "den du dann gern überall links unten
overlayen lässt für Admins und Collaborateure"). Elevated-access → it may use the red accent.

The three directions must differ in the subheader concept above all (user asked in P5: "überlege
ob der Subheader immer oben sein muss oder z. B. an der linken Seite im freien Bereich bei
schmalen Seiten, wo würde das brechen?"). Suggested directions (refine freely, keep them far
apart):
- **A · Holo-Deck** — subheader as a floating glass bar under the (hiding) header; search is a
  command-line field in it; overlays as holo panels.
- **B · Cockpit-Rail** — on narrow content pages the subheader moves into a LEFT rail in the free
  space (crumbs vertical, search, section nav, actions); on tool pages it is a top toolbar; show
  explicitly where it breaks (tablet portrait / phone → collapses to a top bar) — answer the
  user's question with the mock itself.
- **C · Morph-Bar** — header and subheader merge into ONE contextual bar that morphs per page
  type (cinematic: invisible/integrated; content: crumbs+search; tool: toolbar); overlays as
  morphing sheets.

Annotation layer: round 1 → top 3–7 annotation pins per design on the decisive spots
(the user's own counts rule: 3 designs, top 3–7 pins).

V1 **Regelwerk (deterministisch)** — `data-view-kind="comparison"` or a plain view with a table:

V2 **Breiten für 4K** — decision view. User on B5: "Uff, das hört sich 0 responsiv für 4K an.

V3 **"Auf dem Handy weitermachen"** — decision view. User: "mach wie bei Hatchit ein Icon: wenn
man darauf klickt ein Popup, welches einem ermöglicht direkt auf dem Handy weiterzumachen im
eingeloggten Zustand ohne erneutes Einloggen — super cool!" (Hatchit is a sibling Angular +
Supabase project.) CHALLENGE DUTY: this hands a logged-in session to another device — a QR that
carries a session/refresh token is a session-hijack vector (shoulder surfing, screenshots, QR in
screen shares). Alternatives: (1) QR with one-time, single-use code valid ~60 s, exchanged
server-side (Edge Function) for a NEW session on the phone, desktop shows "Handy verbunden" +
can revoke — RECOMMENDED; (2) magic link via email; (3) QR + confirm on desktop (device approval)
like WhatsApp Web inverted; (4) passkey/cross-device FIDO; (5) QR containing the current
refresh token — REJECTED (explain why). The QR always encodes the CURRENT page URL as deep-link
target so the phone opens exactly where the user is. Show the popup mock in the views or on the
phone screen of each design.

V4 **Suche — Kontext-Ranking** — decision view or explainer: how results are grouped/ranked by
where you search (gallery → images first, ship page → components/weapons of that ship first,
codex index → ships, HQ → own hangar), but "im Zweifelsfall überall z. B. (s)ein Schiff finden";
top-x per group; quick actions per result type (e.g. ship: compare, add to hangar, open loadout

> 3 words → offer "Companion fragen". Alternatives for where search lives on CINEMATIC pages,

## Constraints from the codebase (round 1 evidence)

- Layout contract per route data (`data.layout`) replaces URL string checks in the shell.
- Header/footer height become tokens; `scroll-padding-top` tied to header height (WCAG 2.4.11).
- Real anchors for every navigation (CLAUDE.md rule), `isPlainLeftClick` gate for overlays.
- No native dialogs/tooltips/selects; `sc-select`, `scTooltip`, `ScConfirmService`.
- Phones: nothing floats under the feedback launcher (bottom-right FAB lane); beta switch sits
  bottom-left.
- Everything ships behind the existing Verse β / beta switch (BetaService) first.
