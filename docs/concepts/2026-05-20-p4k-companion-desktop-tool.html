§ 1Runtime & Tech-Stack

Du hast gesagt „orientier dich am SC-Companion-Installer". Der Original-CIG-Installer nutzt Electron. Visuell passend ist Electron — technisch gibt es bessere Alternativen für unseren Use-Case (große File-IO, Multi-Threading, kleine Binary).

A

Tauri 2 (Rust + Webview2)

Empfehlung
Binary ~8–15 MB Rust für IO/Threading HTML/CSS/JS (= unsere Web-Stack-Sprache!) für UI

Webview2 ist auf Windows 10/11 schon installiert. Rust-Side macht Disk-IO, ZIP-Streaming, Hashing — alles schnell & speichersicher. UI nutzt dieselben CSS-Variablen wie die Web-App → 1:1 visuelle Konsistenz „for free". Threading via Rust-Rayon ist trivial.

  • Visuelle Symmetrie mit Web-App ohne Extra-Aufwand
  • Sehr klein → GitHub-Release-friendly, schneller Download
  • Rust = beste Wahl für gigabyte-große ZIP-Streams
  • Sandbox-Security ab Werk (anders als Electron)
  • Rust-Lernkurve für dich (falls noch nicht da)
  • Keine Node-Module — manche Libs muss man selbst Rust-portieren
  • Webview2-Runtime nötig (Win11 hat sie, Win10 evtl. nicht — Tauri-Installer kann sie nachziehen)
B

Electron + Node + Angular

Binary 80–130 MB NPM-Ökosystem SC-Installer-Choice

Was CIG für den realen SC-Installer nutzt. Du könntest die Angular-Komponenten der Web-App teilweise wiederverwenden. RAM-hungrig, große Binary, aber „so wie SC selber's macht".

  • Maximaler Code-Reuse mit Angular-Web-App
  • NPM-Libs für alles (yauzl, fast-glob, etc.)
  • Vertraute Stack-Familie
  • ~100 MB Download — Friction beim Verteilen
  • RAM 200–400 MB im Idle
  • Node-Streams sind langsamer als Rust für GB-große ZIPs
  • Bekannte Security-Issues wenn falsch konfiguriert (nodeIntegration etc.)
C

.NET 8 (WinUI 3, self-contained, AOT)

Binary ~25 MB Windows-only OK (SC ist Windows-only) XAML UI

Maximaler Windows-Native-Speed. AOT-Compile → sehr schneller Start. XAML kann den SC-Style nachstellen, aber doppelte Pflege gegenüber Web-CSS.

  • Beste Disk-/Threading-Performance auf Windows
  • Echtes Native-Look-and-Feel möglich
  • Doppelte Style-Pflege (XAML ≠ CSS)
  • Cross-Plattform fällt weg (irrelevant hier — SC ist Win-only)
  • Stack-Bruch mit der Web-App
D

Go + Wails v2

Binary ~15 MB goroutines = Threading Webview UI

Ähnlich Tauri-Charakter, aber mit Go statt Rust. Goroutines sind sehr ergonomisch für parallele File-Scans.

  • Go ist einfacher zu lernen als Rust
  • Sehr gutes IO-Throughput
  • Selbe Web-UI-Sprache wie Tauri
  • Kleinere Community für Game-Asset-Parsing als Rust
  • Wails-Ökosystem weniger reif als Tauri
  • GC-Pausen können bei sehr großen Streams stören

§ 2Game-Discovery & Versions-Erkennung

Wie findet das Tool die installierten Channels und deren Data.p4k? Du sagtest „alle installierten erkennen, standardmäßig angeklickt".

A

RSI-Launcher-Konfig + Standard-Pfade

Empfehlung
RSI-Launcher schreibt JSON-Configs Fallback: bekannte Pfade

Der RSI-Launcher pflegt unter %APPDATA%\rsilauncher\ JSON-Files mit installierten Channels + Install-Pfaden. Lesen, parsen, gefundene Channels mit Versions-Tag anzeigen. Fallback: scannt typische Pfade (C:\Program Files\Roberts Space Industries\StarCitizen\{LIVE,PTU,EPTU,TECH-PREVIEW}\) wenn JSON fehlt.

  • Zero Manual Input wenn RSI-Launcher genutzt wird (Standard-Case)
  • Versions-String kann direkt aus Launcher-Config gezogen werden
  • Robust gegen Custom-Pfade (User hat z.B. auf D:\ installiert)
  • Bricht wenn CIG die Launcher-Config-Struktur ändert
  • User ohne RSI-Launcher (Manual-Install via Backup) fallen auf Fallback
B

Filesystem-Scan + P4K-Header-Sniff

Crawlt typische Drives Liest erste 1 KB jeder .p4k

Scannt C:/D:/E: nach **/StarCitizen/**/Data.p4k (max-depth 6). Liest die ersten 1 KB jeder gefundenen P4K, sucht nach Versions-Strings im ZIP-Comment-Bereich.

  • Funktioniert ohne RSI-Launcher
  • Erkennt auch verschobene Installationen
  • Disk-Crawl auf großen HDDs dauert
  • Versions-Erkennung aus Header-Sniff ist heuristisch und kann irren
C

Reine Manual-Auswahl (Folder-Picker)

User wählt OrdnerEinfachste Implementation

„Klick auf 'Ordner wählen', wähle deinen StarCitizen-Channel-Folder". Tool liest dann nur das eine Verzeichnis.

  • Trivial zu implementieren
  • 100% deterministisch
  • Schlechte UX vs. Vorgabe „erkennt automatisch"
  • Mehrere Channels = mehrere manuelle Picks
Empfehlung: A als Primary, B als automatischer Fallback, C als manueller Override-Button („Pfad selbst angeben"). Drei Layer, robust.

  • Falsche Defaults = User crashed sein System

§ 5Validation & Integrity-Check

Du willst, dass das Tool zeigt „extrahierte Daten erscheinen valide / semantisch korrupt / unvollständig". Wie messen wir das?

A

Hash-Vergleich gegen Last-Known-Good

Server hat Hashes der zentralen P4K-Files für jeden bekannten Patch. Tool meldet Mismatch → „neuer/unbekannter Patch, könnte Format-Drift bedeuten".

  • Trivial zu implementieren
  • Schneller Smoke-Test
  • Detektiert nur „Datei verändert", nicht „Daten kaputt extrahiert"
B

Heuristik-Counters mit Schwellwerten

„Erwarte mindestens N Schiffe, M Items, P Localization-Keys". Wenn Counter unter Schwelle → gelb. Wenn weit unter → rot.

  • Findet „Extraktion frühzeitig abgebrochen"-Fälle
  • Schwellen aus letzten Patches gelernt
  • Schwellen müssen gepflegt werden
  • Sieht keine subtilen Schäden (z.B. ein Schiff hat keine Stats)
C

Schema-Validation + Quality-Score 0–100

Empfehlung

Jede extrahierte Entity gegen JSON-Schema. Felder-Coverage pro Entity-Typ (z.B. „Schiff XYZ hat 18/22 erwartete Felder → 81%"). Aggregat-Score über alles → grün/gelb/rot. Pro Entity die fehlenden Felder anzeigbar.

  • Findet semantische Schäden früh
  • Score eignet sich als Upload-Gate („nur uploaden wenn >90%")
  • Transparent für User („hier fehlt was")
  • Schemas müssen gepflegt + erweitert werden
D

Server-Side Diff gegen Last-Good-Extract

Empfehlung (Ergänzung)

Nach Upload diff'ed der Server gegen den letzten validen Extract derselben Patch-Familie. „98% der erwarteten Entities vorhanden, 12 neue Items, 2 verschwundene".

  • Beste Detektion von „diese Extraktion hat was übersehen"
  • Schöne Patch-Diff-UX as a side-effect
  • Setzt voraus dass es einen Vorgänger-Extract gibt (Bootstrap-Problem)
Empfehlung: C lokal im Tool (als Upload-Gate) + D server-side (als Patch-Diff-Feature). A reicht als zusätzlicher Smoke-Check. B kann man sparen — C subsumiert das.

§ 6Security-Modell — Auth + Binary-Pairing

Du willst „doppelte Security": Tool prüft Website, Website prüft Tool. Hier vier Ausprägungen, von minimal bis paranoid.

A

Browser-Token-Pairing (Loopback-OAuth)

App startet lokalen Loopback-Server (z.B. http://127.0.0.1:46821), öffnet Browser bei sc-companion.vercel.app/desktop/auth?cb=...&state=.... User loggt sich ein (Supabase Auth), Website redirected zum Loopback mit signiertem Token. App nutzt Token für Upload. Binary selbst hat keine Identität.

  • Standard-OAuth-Flow, gut verstanden
  • Keine Cert-Infrastruktur nötig
  • „Doppelte Security" nur einseitig (Web prüft User, nicht Binary)
  • Token-Diebstahl = Upload-Privileg fremd nutzbar
B

Code-signed Binary + Loopback-Token + Server-Hash-Check

Empfehlung

A + Binary ist code-signiert (EV-Cert oder Self-Signed mit Manifest). Beim Upload sendet die App ihren eigenen SHA-256-Hash im Header. Server prüft: Hash steht auf der „aktuell akzeptierten Binaries"-Whitelist (Vercel-KV). Mismatch → Upload-Reject. So weiß der Server: dieser Upload kommt aus einer von uns publizierten Version.

  • Erfüllt „doppelte Security" sauber
  • Per-Release-Revoke möglich (alte Versionen abschalten)
  • Self-Signed reicht zunächst — EV-Cert ($300/yr) später wenn Windows-SmartScreen nervt
  • Hash-Whitelist muss bei jedem Release gepflegt werden (CI-Step)
  • Hash-Spoof möglich wenn Angreifer eine alte gültige Version weiterverteilt — Mitigation: Time-Window pro Hash
C

B + Machine-Fingerprint-Binding

Beim ersten Login wird die App an Machine-ID (Win-Volume-Serial + CPU-ID) gebunden. Wenn Binary auf anderer Maschine läuft → erzwungener Re-Pair.

  • Schützt vor „kopier die App auf einen anderen PC"
  • UX-Hostile bei Hardware-Wechsel
  • Privacy-Issue (Fingerprint persistieren)
  • Overkill für 2–10 Collaborators
D

Build-on-Demand — Per-User-Binary

Server (GitHub-Action) baut beim Download-Click eine binary mit eingebettetem User-Token (24h gültig). Maximale Bindung, max-Aufwand.

  • Tightest Coupling möglich
  • Token-Rotation built-in
  • GitHub-Actions-Minutes-Cost
  • User wartet 30–60 s auf Build
  • Binary-Cache zerstört → keine zentrale Verteilung

§ 10Distribution & Auto-Update

Wie kommt der User an die App, und was passiert wenn eine neue Version raus ist (z.B. P4K-Format hat sich geändert)?

A

GitHub-Releases als Quelle, In-App-Update-Check

Empfehlung

Tool-Binaries werden als GitHub-Release-Assets veröffentlicht (private Repo, signed URLs via Edge-Function — nur authentifizierte collaborator/admin sehen den Download-Button). App pingt beim Start die GitHub-API → „Update verfügbar" Toast. Tauri/Electron haben Updater-Module dafür.

  • Zero Hosting-Cost
  • Delta-Updates möglich (Tauri-Updater)
  • Audit-Trail (jede Version steht im Repo)
  • Private Repo + signed Download-URLs = etwas Edge-Function-Glue
B

Force-Update bei Format-Inkompatibilität

Empfehlung (Ergänzung)

Wenn Server-Side bekannt ist „P4K-Schema-Version X braucht App ≥ Y", verweigert der Upload-Endpoint Uploads von älteren Apps. App zeigt erzwungenes Update-Dialog. Verhindert kaputte Uploads aus alten Versionen.

  • Schützt Datenqualität proaktiv
  • Vermeidet „warum funktioniert mein Upload nicht"-Tickets
  • Friction für User wenn Internet down während Update
C

Eigener Update-Server

Edge-Function auf Vercel als Update-Manifest. Mehr Kontrolle (z.B. Staged Rollouts, A/B), mehr Code zu warten.

  • Staged Rollouts möglich
  • Mehr Infrastruktur für derzeit minimalen Mehrwert
D

Auto-Update silent im Hintergrund

App lädt + installiert Updates ohne Nachfrage. Tradeoff: convenient vs. „mein Tool hat sich plötzlich geändert".

  • Maximum convenience
  • Bei breaking changes irritierend
  • User-Trust kann sinken („was hat es jetzt schon wieder gemacht")

§ 11Offene Fragen & Nice-to-Have

Punkte, die ich nicht selbst entscheiden will, die aber spätestens vor Implement-Klick geklärt sein sollten.

  1. Code-Signing-Cert: EV-Cert ~$300/Jahr vs. selbstsigniert (Windows-SmartScreen-Warnung beim ersten Run, verschwindet aber durch „mehr Info → trotzdem ausführen" → SmartScreen lernt). Für 2–10 User: selbstsigniert reichbar. EV-Cert wenn Public-Distribution irgendwann gewünscht ist.
  2. Tool-Lokalisierung: nur EN oder DE+EN parallel zur Web-App? Web-App nutzt ngx-translate mit de.json/en.json — gleiche Files in Tool wiederverwenden ist trivial.
  3. Telemetrie: Opt-in-Send-Logs („mein Lauf hat versagt, hier ist der Trace") an einen Sentry/Glitchtip? Wäre nützlich, aber Friction beim ersten Run.
  4. Conflict-Handling beim Upload: wenn 2 Collaborators denselben Patch hochladen — Quality-Score-basiert die bessere behalten, beide behalten und Diff anzeigen, oder „first-wins"?
  5. Lokale Cache-Persistenz: Tool extrahiert in %LOCALAPPDATA%\sc-companion\extracts\{patch-id}\. Soll der Cache nach Upload bestehen bleiben („Re-Upload" möglich) oder direkt nach erfolgreichem Upload gelöscht werden?
  6. UI-Sprache der Concept-Phase: implementieren wir das Tool primär für dich (DE-UI) oder direkt mehrsprachig? Mehrsprachig kostet ~+20% UI-Zeit.
  7. License der Desktop-App: Source im selben Repo (Monorepo) oder eigenes Repo? Lizenz: MIT (offen), Source-Available (non-commercial), oder proprietary-internal?
  8. Testen autonom: du hast „Teste eigenständig" geschrieben. Tauri/Electron in CI testbar — aber „Lade echte 100 GB P4K und schau ob's funktioniert" geht nur mit echter Hardware. Frage: ist eine kleine synthetische Test-P4K (~50 MB) als Fixture für dich genug, oder soll ich darauf bestehen, dass du selbst einmal die echte P4K reinwerfen musst, bevor wir „done" sagen?

AMaximal-Scope — was genau soll extrahiert werden?

Du hast „Maximal" (3D-Modelle + Render-Previews) gewählt, Minimal & Standard explizit verworfen. Bevor wir das umsetzen — Realitäts-Check, dann granulare Sub-Auswahl.

Was „Maximal" in der SC-Welt real bedeutet: 3D-Assets liegen als .cgf/.cga/.skin (CryEngine Custom-Geometry, proprietär). Open-Source-Parser (cryxml, cgf-converter) existieren, aber CIG ändert Format-Details mit Major-Patches → laufender Maintenance-Aufwand. Bekannte CIG-Reaktionen auf 3D-Extraktion: der „SC 3D Viewer" wurde 2019 mit DMCA-Notice geschlossen. „Hangar Companion" 2021 ähnlich. Aufbereitete Stats/Icons werden geduldet (erkul.games, starcitizen.tools laufen seit Jahren). Heißt: je weiter wir in die 3D-Welt gehen, desto höher das Risk-/Wartungs-Profil.

Lass uns „Maximal" als 4-stufige Skala feinjustieren. Markiere präzise, was du WIRKLICH brauchst — alles, was Verwerfen kriegt, fliegt raus:

A1

BSecurity — wie passt OAuth-only zu „doppelter Security"?

Du hast nur Loopback-OAuth gewählt — Code-Signing-Binary-Whitelist, Machine-Bind und Per-User-Build verworfen. Das ist sauber implementierbar, aber widerspricht deiner ursprünglichen Forderung „sozusagen doppelte Security von Website und Programm her". Drei Wege aus der Spannung:

B1

OAuth-only, Punkt — „ich vertraue meinen Collaborators"

Du hast 2–10 vertrauenswürdige Personen. Token-Klau ist möglich, aber realistisch wenig. Der Token hat z.B. 7 d TTL und kann jederzeit revoked werden. Doppelte Security wird damit explizit aufgegeben, dafür ist die Architektur sehr einfach (kein Cert, keine Whitelist-Pflege).

  • Einfachste Implementation, minimal Wartung
  • Token-Revoke = Notbremse
  • Wenn Binary leakt, kann jeder authentifizierte User uploaden — Vertrauen zum Tool fehlt
B2

OAuth + Release-Token-Header (kein Code-Cert nötig)

Empfehlung

Beim Build der Binary wird ein Release-Token als Build-Constant eingebettet (UUID, pro Release einzigartig). Beim Upload sendet die App diesen Header: X-SC-Release-Token: <uuid>. Server hat eine Allowlist der aktuell-akzeptierten Release-Tokens (3 Versionen rotierend) — Mismatch → Reject. Kein EV-Cert nötig, kein Hash-Computing, nur ein Build-Step der vor dem Upload den Token in die env injiziert + ein Server-Check.

  • Erfüllt „doppelte Security" sauber — Tool muss aus offiziellem Release stammen + User muss authentifiziert sein
  • Release-Rotation = automatischer Forced-Upgrade-Pfad
  • Trivial in CI: GitHub-Actions setzt env-var pro Release-Build, Server kennt die Allowlist via Edge-Function-Secret
  • Wer die Binary disassembliert, kann den Token extrahieren — aber dafür müsste er die spezifische Release-Binary haben, die nur Collaborators downloaden können (Loop: Binary-Download ist schon auth-gated via Edge-Function mit Role-Check)
B3

OAuth + Per-User-Build (was du ursprünglich beschriebst)

Auch wenn du Per-User-Build in Iter 1 verworfen hast — es matched 1:1 deine Aussage „dass das eine ausführbare programmversion ist die von dem nutzer der es nun hochlädt heruntergeladen wurde". GitHub-Action baut beim Download eine Binary mit eingebettetem User-Token. Re-Aufnahme, falls ich dich falsch interpretiert habe.

§Offene Fragen & Phase-2-Punkte

Diese Punkte sind bewusst auf später verschoben. Häkchen lassen = später als GitHub-Issue tracked (Default: alle an). Verwerfen = ich verfolge das gar nicht weiter.

Hinweis: die Concept-Bridge ist beendet — der „Issues erstellen"-Button im Panel funktioniert in dieser Session nicht mehr. Wenn du die Issues willst, sag mir einfach „erstell die Issues für die angehakten Punkte" und ich tu's direkt.

Q1

Echter P4K-Extraktor (yauzl-Stream vs. native Sidecar)

yauzl liest Standard-ZIP, aber CryEngine-spezifische Streams (CGF/CGA/SKIN) brauchen evtl. einen nativen Rust/C++-Sidecar. Recherche-Tranche: 2–4h, dann Entscheidung.

Q2

Render-PNG-Architektur (§A2)

3-6 standardisierte Schiff-Views erzeugen. Option (a): lokal mit headless three.js im Electron-Main. Option (b): Mesh wird kurzzeitig an einen Render-Worker (Edge-Function mit Headless-Chrome? Eigener Service?) geschickt. Design-Decision-Heavy.

Q3

Schema-Score-Validator mit echten JSON-Schemas

Pro Entity-Typ (Ship, Weapon, Component, Item) ein JSON-Schema-File. Coverage % aggregiert zu 0..100-Score. Brauche Beispiel-Daten aus Q1, dann ~3h Schema-Authoring + Validator-Wiring.

Q4

Server-side Diff gegen Last-Known-Good

Neue Edge-Function: vergleicht neuen Bundle gegen jüngsten Bundle gleicher Channel-Familie. Liefert „98% der Entities vorhanden, 12 neue, 2 verschwundene". Setzt voraus, dass mindestens 2 Bundles für eine Channel-Familie existieren — Bootstrap erstmal manuell.

Q5

Synthetische P4K-Fixture für E2E-Extractor-Tests

~50 MB ZIP mit repräsentativem Mix aus CryEngine-XML-Files, Icons, Component-Manifests — KEINE copyrighted Assets. Generator-Script in desktop-tool/test/fixtures/build.ts. ~4h.

Q6

Auto-Update-Flow (electron-updater)

App pingt GitHub-API beim Start, zeigt „Update verfügbar"-Toast. Plus Force-Update wenn der Server eine inkompatible P4K-Schema-Version meldet (§ 10 B). ~3h.

Q7

Code-Signing entscheiden (self-signed vs. EV-Cert)

Für 2-10 Collaborators: self-signed reicht (SmartScreen-Warnung beim 1. Run, dann gelernt). EV-Cert (~$300/yr) für später wenn Public-Distribution. Soll ich einen Quick-Self-Signed-Setup machen?

Q8

Telemetrie (opt-in) — Sentry/Glitchtip

„Mein Lauf hat versagt — hier ist der Stack-Trace"-Button. Opt-in beim Erst-Start. Nützlich aber Friction, vor Phase 2 vermutlich Overkill.

Q9

Conflict-Handling bei Duplicate-Patch-Upload

Bei UNIQUE (channel, patch_version, uploaded_by) kollidiert ein Re-Upload desselben Collaborators. Was bei verschiedenen Collaborators? Higher-Quality-Score gewinnt? Beide behalten + Diff anzeigen? Heute: erste Insertion gewinnt, andere reject.

Q10

Lokale Cache-Persistenz

Tool extrahiert in %LOCALAPPDATA%\sc-companion\extracts\<patch-id>\. Nach Upload: löschen oder Re-Upload-fähig behalten? Settings-Toggle „Cache nach Upload behalten" Default off.

Q11

Lizenz der Desktop-App

Monorepo = Web ist proprietär (kein LICENSE-File). Desktop-Tool kann separat sein — MIT (offen für Forks), AGPL (offene Klon-Pflicht), oder „source-available, non-commercial". Default-Vorschlag: keine Lizenz wählen, Tool bleibt proprietary-internal bis Public-Beta.

Q12

Locale-Translator finden (FR/ES/PT/RU/ZH)

Stubs liegen, echte Übersetzungen brauchen Native-Speaker oder DeepL+Review. Phase 3 Polish-Item — nicht blockierend für MVP-Beta.
