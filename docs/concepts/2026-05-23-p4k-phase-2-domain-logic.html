§ 1P4K-Parser-Architektur

P4K ist ein ZIP-Archiv mit speziellem ZSTD-Encoding (CIG hat seit ~3.18 von zlib auf custom-ZSTD migriert). Vier Wege.

A

Pure Node — yauzl-stream + ZSTD-decoder

Bundle ~+1 MB Async streams No native deps

yauzl liest ZIP-Central-Directory, streamt Entries. Für custom ZSTD CIG-Variant: @mongodb-js/zstd oder native zstd-napi. Pro-Schiff/Item-XML wird im Stream gelesen, XML-Parser (fast-xml-parser) übersetzt nach JSON.

  • Reine Node, keine native Builds in CI
  • Cross-platform (Win/Mac/Linux dev)
  • Easy debugging
  • Node-Streams sind ~3-5× langsamer als nativ für 80 GB+ ZIPs
  • ZSTD-Decode in JS = CPU-Bound, Single-Thread (außer worker_threads)
  • CGF/CGA-Decode: müsste auch in TS oder JS (langsam)
B

Node yauzl + Rust-Sidecar für Heavy-Lifting

Empfehlung
Sidecar ~5 MB napi-rs Parallel-friendly

Node-Layer macht UI/IPC/Orchestration. Rust-Sidecar (via napi-rs) liest P4K + dekompimiert ZSTD + parsed CGF/CGA. JS bekommt JSON-Records via Channel.

  • Performance wo's drauf ankommt (Disk-IO + Decompress), Komfort wo nicht (UI)
  • Rust-Crates für CryEngine-Parser existieren (cry-formats)
  • Multi-Threading via rayon trivial
  • Sidecar ist statisch gelinkt → 1 .node-Datei pro Platform
  • napi-rs braucht Rust-Toolchain im CI (npm publish prebuilt binaries)
  • 2 Sprachen im Code
C

Full Rust-Sidecar via Tauri-Sidecar-Pattern

Standalone Binary IPC via stdio/socket

Komplette Extraction-Pipeline als externes Rust-Binary. Electron spawnt es als Child-Process, kommuniziert via JSON-RPC über stdio.

  • Maximaler Performance-Gewinn
  • Rust-Code unabhängig testbar (auch CLI-tauglich)
  • IPC-Boilerplate (vs. napi-rs direkter)
  • Child-Process Lifecycle-Management
  • Doppelte Binaries: Electron + Rust → größerer Release
D

WebAssembly — Rust → WASM in Renderer-Worker

In-Browser Memory-Bottleneck

Rust kompiliert zu WASM, läuft im Renderer-Worker. JS-Side liest File-Handle.

  • Singular Build-Pipeline, kein Native
  • WASM hat 4 GB Memory-Cap — bei 80 GB P4K = Streaming-Only-Workflow, komplex
  • File-System-Access in Renderer = Sandbox-Bruch oder File-Picker-Friction
  • Schlechtere Perf als native

§ 2CryEngine-Format-Parser (CGF/CGA/CHR)

Da wir keinen 3D-Web-Viewer bauen, brauchen wir aus CGF/CGA nicht die volle Geometrie — nur Metadaten (Bounding-Box, Mount-Points, Hardpoint-Hierarchie, Material-Refs). Das macht den Parser deutlich kleiner.

A

Existierender Port: cgf-converter (C#, MIT)

Open-Source C#-Tool von Markemp, GitHub-Sterne 200+, wird gepflegt. Port nach Rust oder TS.

  • Battle-tested für SC + andere CryEngine-Games
  • Vollständige Format-Doku darin
  • C# → Rust/TS-Port ist Mehrwoche-Arbeit
  • Pulls more than we need (full mesh extraction)
B

Rust-Crate cry-formats direkt

Empfehlung

Existierende Rust-Crate (~v0.4), parsed CGF/CGA-Header + Chunks. Wir nutzen nur die Chunks, die wir brauchen (BoundingBox, NodeHierarchy, MtlNameChunk, IncludedObjects). Skip-Patterns für volle Meshes.

  • Reused, minimal eigener Code
  • Passt zu § 1 B (napi-Sidecar) — Rust-zu-Rust
  • Streaming-friendly für große Files
  • Crate ist klein/jung — evtl. müssen wir contributen
C

Custom-Minimal-Parser (von 0 aufgesetzt)

Wir lesen das CGF-Format direkt nach Spec: Chunk-Header parsen, nur die 4-5 Chunks lesen die uns interessieren, alles andere skippen.

  • Kein Dependency-Risk
  • Exact size: parsed nur was wir brauchen
  • Volle Pflege bei CIG-Format-Änderungen liegt bei uns
D

Skip — CGF/CGA gar nicht parsen, nur XML-Definitionen

Phase-1-Scope hat 3D-Mesh raus. Vielleicht reichen die *.xml-Manifests wirklich aus: Schiffe sind in Data/Objects/Spaceships//.xml definiert, inkl. Hardpoint-Tree. Component-Tree extrahieren wir aus XML, nicht aus CGF.

  • Massiv weniger Code + keine CGF-Format-Drift-Maintenance
  • Render-PNGs (§ 3) brauchen Mesh — wenn die woanders herkommen, brauchen wir CGF nicht
  • Falls XML unvollständig ist (Mount-Geometrie nur in CGF), fehlen Daten
Wichtig: wenn D gewählt wird, hängt § 3 (Render-PNG) davon ab — entweder gar keine Renders (statisch von SC-Wiki), oder eine andere Mesh-Quelle.

§ 3Render-PNG-Pipeline (A2 aus Phase 1)

Pro Schiff sollen 3-6 standardisierte Views (Front/Side/Top/Iso) als PNG entstehen — für Web-App. Mesh darf nicht persistiert werden, nur das PNG-Ergebnis. Wo läuft der Renderer?

A

Lokal · Headless Three.js in Electron-Hidden-Window

Empfehlung

Electron spawnt ein verstecktes BrowserWindow (`show: false`, OffscreenRender). Three.js lädt das Mesh (vom Parser geliefert), positioniert Kamera, ruft `renderer.render()`, liest Canvas als PNG-Buffer, übergibt an Main → wird ins Bundle gelegt → Mesh wird verworfen.

  • Kein Server-Roundtrip — Mesh bleibt auf dem User-Rechner
  • three.js ist Battle-Tested, GLTF/OBJ-Loader vorhanden
  • GPU-beschleunigt (über Chromium's WebGL/ANGLE)
  • Pro Schiff ~200ms-2s, 60 Schiffe = ~2-5 min auf normaler GPU
  • Headless-Rendering in Electron hat manchmal GPU-Treiber-Issues auf älteren Maschinen
  • Mesh muss CGF → glTF konvertiert werden (oder direkt buffer-geometry-fed)
B

Lokal · Rust-native Renderer (wgpu in Sidecar)

Sidecar nutzt wgpu (Vulkan/Metal/DX12-Abstraktion). Mesh → Renderpipeline → PNG. Komplett ohne Browser.

  • Sehr schnell (native GPU access)
  • Lean — kein 50 MB Chromium-Hidden-Window
  • wgpu+Mesh-Loader-Setup ist Code-aufwendig
  • Material/Shading-Treue niedriger als three.js (rohe Geometrie)
C

Server · Edge-Function spawnt Headless-Chrome

App lädt Mesh-Blob temporär zu Supabase-Storage. Edge-Function spawnt headless-chromium mit three.js-Script, rendert, speichert PNGs in Bucket. Storage-Mesh wird nach 1h auto-gelöscht (TTL-Policy).

  • User-Maschine unbelastet
  • Renderer-Code zentral wartbar (kein Client-Update nötig)
  • Mesh-Upload (zeitweise) bedeutet Mesh verlässt den User-PC → Vertrauensbruch falls Lizenz-Bedenken
  • Edge-Function-Timeout 150-400s, GPU-Access nicht garantiert
  • Vercel/Supabase-Edge hat kein Chromium pre-installed → custom Container nötig
  • Kosten: pro Render-Bundle X-Sekunden Compute
D

Hybrid · Render lokal, but Render-Engine als WASM-Modul vom Server

Wie A, aber die Render-Logic kommt als WASM-Modul vom Server (lazy-loaded). So sind Verbesserungen am Renderer ohne App-Update verteilbar.

  • Renderer-Updates ohne App-Release
  • Mesh bleibt lokal
  • Komplexer Update-Mechanismus für ein selten-aktualisiertes Subsystem
Hängt von § 2 ab: wenn § 2 D („Skip CGF") gewinnt, brauchen wir gar kein Mesh → kein Renderer. Render-PNGs müssten dann aus anderen Quellen (offizielle SC-Marketing-Bilder, starcitizen.tools, etc.). Falls dem so ist, bitte das gesamte § 3 verwerfen.

§ 4Schema-Score-Validator

Pro Entity-Typ (Ship, Weapon, Component, Item) ein Schema. Coverage-% pro Entity → Aggregat-Score 0-100. Wo lebt die Schema-Definition?

A

JSON-Schema + AJV

Klassisches JSON-Schema (Draft 2020-12). AJV im Desktop-Tool + im Web (gleiche Schemas). Schemas leben in `desktop-tool/src/schemas/*.json`.

  • Industriestandard, viele Tools
  • Schemas sind JSON → kein Build-Step
  • Keine TypeScript-Type-Inference ohne Extra-Generator
  • JSON-Schema-Syntax ist verbos
B

Zod-Schemas (TypeScript-First)

Empfehlung

Schemas als TS-Code (`z.object({...})`). Type-Inference automatisch. Validation + Parsing in einem.

  • End-to-end typesafe — Web-App ↔ Desktop-Tool ↔ Edge-Functions teilen Types
  • Schemas + TS-Types + Validator in einer Quelle
  • Coverage-Metrik einfach (Failed-Field-Set aus ZodError)
  • Schema-Code muss in shared Monorepo-Package (z.B. `shared/schemas/`)
  • Edge-Functions (Deno) brauchen Zod-Version die Deno-kompatibel ist (es gibt eine)
C

TypeBox (JSON-Schema mit TS-Types)

Best-of-both: Schemas in TS-Code, Output ist JSON-Schema, TS-Types werden inferiert. Validation läuft mit AJV.

  • Echte JSON-Schemas exportierbar (für externe Tools)
  • TS-Types wie Zod
  • 2 Validatoren (TypeBox-Build + AJV-Runtime)
D

Custom DSL für SC-spezifische Felder

Eigene Schema-Sprache (z.B. YAML) mit SC-spezifischen Constraints wie „Mount-Size muss 1-12 sein". Validator parsed das.

  • Domain-spezifisch beschreibbar
  • Yet-another-DSL, niemand sonst kennt das
  • Müssen wir selbst maintainen

§ 5Server-Diff gegen Last-Known-Good

Beim Bundle-Upload soll der Server gegen den letzten validen Bundle derselben Channel-Familie diff'en — „98% der Entities da, 12 neue, 2 verschwundene". Wo + wie?

A

Edge-Function nach Upload (sync)

Empfehlung

Neue Edge-Function `ingest-bundle`: validiert Release-Token + Auth, ruft `diff_bundle(new_id, prev_id)` Postgres-RPC, speichert Diff-Result als Spalte auf `p4k_bundles`. Response ans Tool: Score + Diff-Summary.

  • User sieht Diff sofort im Desktop-Tool
  • Atomic: validate + ingest + diff in einer Transaction
  • Edge-Function-Timeout limitiert (150s Free, 400s Pro) — für sehr große Diffs evtl. Problem
B

Pure Postgres-Function (jsonb-Diff)

`diff_bundle(new_id, prev_id)` als pure Postgres-Function. Edge-Function ruft sie auf, oder direkt vom Tool über RPC. Logik in SQL.

  • DB-nahe, kein Edge-Function-Cold-Start
  • RLS-konform out of the box
  • SQL ist nicht ideal für komplexe Diff-Logik (Set-Operations gehen, aber Sub-Field-Diffs werden hairy)
C

Async via Postgres-Trigger + Pg-Queue

Insert auf `p4k_bundles` triggert pg_cron-Job, der diff'ed im Hintergrund. Web-App polled `diff_status` für UI-Update.

  • Kein Timeout-Risk
  • Tool muss nicht warten
  • User sieht Diff erst nach Polling-Delay
  • pg_cron-Setup zusätzlicher Infra
D

Lokal im Desktop-Tool vor Upload

Tool ruft die Web-App per RPC nach dem letzten Bundle derselben Channel-Familie, downloaded dessen JSON-Manifest, diff'ed lokal, schickt das Diff-Result mit beim Upload.

  • Server-Compute = 0
  • User sieht Diff schon vor Upload-Klick
  • Tool muss vorigen Bundle downloaden (kann groß sein)
  • Tool-Logic doppelt: Diff-Code muss exakt zu Server-Schema passen

§ 6Auto-Update-Flow

Phase 1: User muss manuell von /desktop downloaden. Phase 2 macht das automatisch.

A

electron-updater + GitHub Releases (Default)

Empfehlung

App pingt beim Start die GitHub-API für die neueste Release. Wenn neuer, lädt sie Delta-Update (über die `latest.yml`-Metadata + blockmap). Toast: „Update verfügbar — installieren?". Bei Restart wird's installiert.

  • Standard-Pfad für Electron-Apps, viel Doku
  • Delta-Updates via blockmap (nur Diff geladen)
  • Nutzt unsere bestehenden GitHub-Releases-Artifacts
  • Private Repo + GH-Releases: jeder User braucht GH-Token im Tool (oder Edge-Function als Proxy)
B

Eigener Update-Endpoint (Edge-Function)

Edge-Function `desktop-latest-release` returned aktuelles Release-Metadaten (Version, URL, SHA). Tool checked das + downloaded selbst. Keine GH-Token-Dependency.

  • User braucht keinen GH-Token
  • Server kann Release-Token-Validation direkt
  • Wir müssen Delta-Update selber implementieren (vs. electron-updater-out-of-the-box)
  • Edge-Function-Caching nötig für viele User
C

Hybrid: A + B (Edge-Func als GH-Proxy)

Empfehlung (Ergänzung)

electron-updater spricht NICHT direkt mit GH, sondern mit unserer Edge-Function. Die ruft GH mit dem service-Token + filtert Release-Metadata für User. So bleibt der GH-Token server-side.

  • electron-updater out-of-box + private-Repo-safe
  • Edge-Function kann Force-Update steuern (siehe Concept Iter 2 § 10 B)
  • Edge-Function-Endpoint muss `latest.yml` + Asset-URLs mit signierten Redirects ausliefern
D

Background-Auto-Install (kein Prompt)

App installiert Updates silent, kein User-Prompt. Wirkt wie Magie aber kann irritieren.

  • Maximaler convenience
  • Breaking-Changes überfallen den User
  • User-Trust kann sinken

§ 7Synthetic Test-Fixture

Damit CI E2E-Extractor-Tests laufen kann, brauchen wir eine kleine fake-P4K mit MIT-licenced Test-Daten. Wie?

A

Generator-Script: desktop-tool/test/fixtures/build-fake-p4k.ts

Empfehlung

Node-Script generiert ZIP-Datei mit:
– 5 fake-Schiffe als XML (eigene Namen: TEST_Falcon, TEST_Sparrow, …)
– 10 fake-Items
– 5 fake-Weapons
– 1 fake-Icon-PNG pro Schiff (procedural)
– keine CGF/CGA (Phase 1 Scope hat 3D raus)

Output: ~5-10 MB ZIP, committed to repo (test/fixtures/synthetic.p4k.zip). CI nutzt es ohne weiter Setup.

  • 100% MIT-clean, kein CIG-Material
  • Deterministic — Tests immer reproduzierbar
  • Erweitert testbar (mehr Schiffe, edge-cases)
  • Script-Code = Zusatz-Wartung wenn Schema sich ändert
B

Echte SC-P4K minimal subsetted

Aus deiner echten Data.p4k 1% extrahieren, in eine kleine ZIP packen. Realistische Daten.

  • 100% realistisches Format
  • Lizenz-Problem: das ist CIG-IP, kein public-repo
  • Müsste private im git-LFS bleiben → CI braucht Secrets
C

JSON-Fixtures (kein ZIP)

Tests umgehen die ZIP-Layer, testen nur den Parser von raw bytes ab. JSON-Fixtures sind das erwartete Output.

  • Schneller, einfacher
  • Tests den ZIP/ZSTD-Layer nicht
D

Drei Fixtures: small/medium/large für Perf-Tests

Empfehlung (Ergänzung)

Drei Varianten von Script A:
– small (~1 MB, 5 Schiffe) — für E2E-Smoke
– medium (~50 MB, 50 Schiffe + Items) — für Performance-Profil-Tests
– large (~500 MB, 500 Schiffe + ZSTD-compressed) — für Stress-Tests (CI optional)

  • Echte Performance-Metriken im CI sammelbar
  • Large variant ist groß für git → S3/Storage-Hosting evtl.

§ 8Code-Signing-Strategie

Heute: Unsigned (SmartScreen-Warning beim ersten Run). Was nehmen wir?

A

Self-Signed Certificate

Eigenes Zertifikat, mit OpenSSL erstellt. Signiert die Binary. Kostenlos, aber SmartScreen warnt trotzdem („Unbekannter Herausgeber").

  • Kostenlos, sofort einsetzbar
  • Besser als gar nichts (Binary-Integrity)
  • SmartScreen-Warning bleibt
  • User muss „Mehr Infos" + „Trotzdem ausführen" klicken
B

EV Code-Signing Certificate ($300/yr)

Sectigo/Comodo/etc. — full SmartScreen-Reputation ab Tag 1. Keine User-Warnings.

  • Zero-friction install
  • Public-distributiontauglich
  • $300/year
  • Cert ist auf Hardware-Token (HSM/USB) — CI-Signing braucht spezielle Setups
C

Azure Trusted Signing (~$10/Monat)

Empfehlung

Neuere Azure-Service: Microsoft-managed Cert + Signing-API. EV-äquivalente Reputation, aber CI-friendly (kein USB-Token). Wurde 2024 GA.

  • EV-Level Reputation, signtool kompatibel
  • CI-friendly über REST-API, kein HSM
  • ~10× günstiger als klassisches EV
  • Azure-Account + Subscription nötig
  • Cert ist nicht „dein eigener" — wenn Microsoft den Service abschaltet, weg
D

Defer — bleibt unsigned bis Public-Beta

Für 2-10 Collaborators reicht SmartScreen-Bypass. Investition erst wenn Public-Distribution.

  • $0
  • User-Friction bleibt

APython-Parser-Architektur (Reset)

Du sagtest: „nutze Python wie im restlichen Projekt, kein 80 GB RAM, Pfad-für-Pfad streamen, es gibt GitHub-Projekte die SC-P4K auf normalen Rechnern extrahieren". Die richtige Library dafür ist klar:

Big Insight aus deiner Recherche-Empfehlung: Stats für Schiffe/Waffen leben NICHT in den XML-Files (die sind nur Metadata-Wrapper), sondern in einer einzigen binären Datei: Data/Game.dcb — der CIG DataCore. Die Tools wie scdatatools parsen genau das. Phase 1 hat das missverstanden — wir hätten gar nicht durch tausende XMLs streamen müssen, sondern 1× durch die DataCore.
A1

scdatatools (Python, MIT)

Empfehlung
Aktiv gepflegt pip-installable Streaming-fähig

github.com/StarCitizenTools/scdatatools — Pure-Python-Library, parsed P4K-Container + DataCore.dcb + Localization + Subsumption. Wird seit ~5 Jahren von der starcitizen.tools-Wiki-Community gepflegt. Streamt durch P4K, lädt nicht das ganze Archiv in RAM.

pip install scdatatools

for entry in p4k.namelist():
    if entry == 'Data/Game.dcb':
        with p4k.open(entry) as fp:
            datacore = DataCore.from_file(fp)
            # iterate entities, write JSON chunks to disk
  • Existiert, getestet, MIT-Lizenz
  • Versteht DataCore (.dcb) — wo die Stats wirklich sind
  • Streaming-API: kein RAM-Spike
  • Python passt zur Restprojekt-Toolchain
  • Übersetzt SC-Localization-Strings direkt mit
  • Python-Runtime im Desktop-Tool ist +20-30 MB (Embedded Python)
  • Pinned-Version-Risiko (CIG-Format-Drift muss von scdatatools upstream gefixt werden)
A2

Custom Python-Parser von 0

Eigener P4K + DataCore-Parser in Python. Mehr Code, volle Kontrolle, keine externe Abhängigkeit.

  • Kein Dependency-Risk
  • Format-Reverse-Engineering = Wochen-Aufwand vs. 1 Tag mit scdatatools
  • CIG-Format-Drift komplett unser Problem
A3

unp4k-Subprocess (C#-Tool als Sidecar)

unp4k ist die populärste P4K-Extraktion (C#). Wir könnten es als Sidecar bundeln (.NET-Binary) und per stdio steuern.

  • Stabilste Tool-Family für SC P4K
  • .NET-Runtime-Dependency (+150 MB bundled, oder System-.NET)
  • Kein DataCore-Parsing in unp4k selbst
  • 3 Sprachen im Stack (TS + Python + C#)
A4

Hybrid — scdatatools für P4K+DataCore + minimal Custom für SC-spezifische Glue

Empfehlung (Standard)

scdatatools als Library, drumherum dein eigener kleiner Python-Wrapper der die Streaming-Strategie steuert: „iteriere alle Ship-Entities aus DataCore, schreibe JSON-Chunk auf Disk pro Schiff, dann nächste Entity-Klasse". Wrapper ist ~200 Zeilen Python.

  • Beste Balance: Library für Heavy-Lifting + Wrapper für SC-Companion-spezifische Logik
  • Streaming + Chunking explizit ins Disk (matched dein „kein 80 GB im RAM"-Wunsch)
  • Etwas mehr Code als A1 pure

BWie kommt Python in den Desktop-Tool-Release?

Electron muss eine Python-Runtime aufrufen können. Drei Wege:

B1

Embedded Python (python-build-standalone)

Empfehlung

Wir bundlen Python-3.12 (~25 MB statisch) ins Release-Verzeichnis. Electron spawnt es als Subprocess für jede Extract-Run. Tool-Total-Size: ~110 MB statt 80 MB.

  • Kein User-Setup-Schritt — Tool „funktioniert einfach"
  • Version-Pin gewährleistet (nie System-Python-Mismatch)
  • scdatatools-Dependencies vor-installiert im Release-Build
  • ~+30 MB Release-Size
B2

System-Python (User installiert + pip install)

User muss Python 3.10+ + scdatatools selbst installieren. Tool ruft `python` aus PATH.

  • Kleines Release (~80 MB)
  • Erst-Setup-Friction
  • Python-Version-Drift potenziell brechend
  • Collaborator-Onboarding wird komplexer
B3

PyInstaller-Bundle des Python-Wrappers

Wir packen unser Python-Wrapper-Script + scdatatools mit PyInstaller in ein einzelnes .exe (~50 MB). Electron ruft das .exe statt python.exe. Cleaner als Embedded Python, single binary.

  • Keine separate Python-Installation visibel
  • CI-Build-Pipeline: PyInstaller läuft in GitHub-Action vor electron-builder
  • PyInstaller-Bundles sind manchmal von Anti-Virus geflagged (false positives)
  • Build-Pipeline doppelt (Python + Electron)

CRender-PNGs — neue Realität

Phase-1-Annahme war: wir bauen einen Three.js-Renderer der Schiffe rendert. Aber: CIG packt selbst „Holo-Viewer"-DDS-Renders pro Schiff in die P4K (zu sehen im Hangar-/Loadout-Screen). Damit fällt der ganze 3D-Renderer-Stack weg.

C1

DDS → PNG direkt aus P4K

Empfehlung

scdatatools extrahiert die Data/Textures/UI/Spaceships/*.dds Files. Konvertierung DDS→PNG mit imageio oder Pillow-Plugin (~2-3 Zeilen Python). Output: ~3-5 PNGs pro Schiff in ~100 ms.

  • Zero Render-Compute — wir kopieren nur
  • Optisch identisch zum Spiel (sind die echten Hangar-Renders)
  • Three.js / wgpu kann komplett gestrichen werden
  • Falls CIG für ein Schiff die DDS nicht gepackt hat → fallback nötig (siehe C2/C3)
C2

Wenn ein Schiff keine pre-rendered DDS hat, lädt three.js das CGF + rendert. Hybrid-Pfad.

  • 100% Schiff-Coverage
  • Wieder voller 3D-Renderer-Stack im Tool, nur für seltene Fälle

  • Externe Dependency — Wiki-API kann downgehen
  • Lizenz-Frage je Wiki-Image klären

Bildlos. Web-App zeigt einen Platzhalter.

DPlausibility-Validator (Klarstellung)

Deine Klarstellung: „nicht jedes Attribut exakt validieren, sondern Plausibilität — Warning wenn Feld nicht gefunden, dann nullable / 0, RSI ändert Schemen". Das ist eine andere Architektur als die 4 Iter-1-Optionen.

D1

Soft-Schema mit „expected fields"

Empfehlung

Pro Entity-Typ (Ship/Weapon/Component/Item) eine Liste von erwarteten Feldern mit Typ-Hint. Validator iteriert: jedes erwartete Feld → fehlt? Warning loggen + Feld auf null/0/default setzen. Score = (gefundene Felder ÷ erwartete Felder × 100). Keine Fehler, nur Warnings.

EXPECTED_SHIP_FIELDS = [
  ('mass', 'number', None),
  ('hp_main_hull', 'number', None),
  ('max_speed', 'number', 0),
  ('weapon_hardpoints', 'array', []),
  # ...
]
for field, type_hint, default in EXPECTED_SHIP_FIELDS:
    if field not in ship_data:
        warnings.append(f'missing field: {field}')
        ship_data[field] = default
score = (len(EXPECTED_SHIP_FIELDS) - len(warnings)) / len(EXPECTED_SHIP_FIELDS) * 100
  • Tolerant gegenüber CIG-Schema-Drift
  • Score-Metrik fällt einfach raus
  • Warnings landen im Upload-Bundle → Admin sieht in Web-UI
  • Kein Zod/AJV/TypeBox nötig — pures Python
  • Field-Liste muss gepflegt werden (aber nur 1× pro Entity-Typ)
D2

Pure Counter-Heuristik (kein Schema)

Validator zählt nur: „N Ships gefunden, M Weapons, P Items". Score = Counts vs. Schwellwerte aus letzten Patches.

  • Minimaler Code
  • Findet keine semantischen Schäden (Schiff X hat keine Stats mehr)
D3

D1 + Counter-Schwellen (kombiniert)

Empfehlung (Ergänzung)

D1 für Feld-Coverage + Counter-Check als zweite Dimension. Score = min(field_coverage, count_score).

EDiff-Spec, History-Sichtbarkeit, Admin-Disable (Klarstellung)

FAuto-Update — Challenge zur Kombination GH-direkt + Silent

Du hast „GH-direkt" und „Silent" gewählt. Beide sind als Einzelfall okay, die Kombination ist riskant. Ich challenge:

Risiko 1 — GH-Token im Binary: private Repo + GH-Releases bedeutet entweder (a) wir embedden einen GH-Token in jede Tool-Binary (jeder User kann ihn extrahieren = potenzielle Repo-Read-Permission) oder (b) wir machen den Release-Bucket public (verliert die „Nur Collaborator kann Tool downloaden"-Eigenschaft aus Phase 1 § 8).
Risiko 2 — Silent: Auto-Install ohne User-Wissen kann genau dann passieren wenn der User gerade einen Extract laufen hat → Tool beendet sich mitten im Lauf, Datenverlust.
F1

So lassen — GH-direkt + Silent (deine Wahl)

Wir embedden einen Read-Only-GH-Fine-Grained-Token (nur Releases-Read-Permission) in die Tool-Binary. Silent-Install passiert nur beim nächsten App-Restart, nie mitten im Lauf (electron-updater-Default).

  • Maximal automatisch — User merkt's quasi nicht
  • Read-Only-Token-Scope minimiert Risk
  • Token-Leak macht Repo-Read-Pivot möglich (private Repos enthalten u.U. Secrets in old commits)
  • User bemerkt Update gar nicht → kann sich „warum macht Tool anders X jetzt" wundern
F2

Hybrid Proxy zurück + Silent

Empfehlung

Edge-Function als Proxy (keine Token im Binary), Silent-Install bleibt. Edge-Func returnt nur die Release-Asset-URLs (signiert, 1h TTL). User braucht nichts zu tun.

  • Beste Sicherheit (kein Token im Client) + automatisch
  • Edge-Func kann zusätzlich Force-Update bei kritischem Format-Drift erzwingen
  • Telemetrie über Edge-Func möglich (welche Tool-Versionen sind im Umlauf)
  • Edge-Func-Endpoint muss gebaut werden (~50 Zeilen)
F3

GH-direkt + Toast-Prompt statt Silent

Wie deine Wahl, aber statt Auto-Install zeigt Tool einen Toast: „Update verfügbar — jetzt installieren? [Ja, jetzt / Beim nächsten Start]". User-Trust hoch, fast so convenient wie Silent.

  • User-Trust durch Sichtbarkeit
  • Verhindert Mid-Extract-Updates
  • User muss 1× klicken
